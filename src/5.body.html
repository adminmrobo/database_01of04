도입 문제 — 한 문장을 표로 바꾸기Problem

"김철수가 지난 10월 5일에 삼각김밥 2개와 커피 1잔을 주문했다." 이 문장에서 표를 만들어야 합니다. 무엇부터 시작할까요?

가문장을 뜯어보면
김철수 → 사람 (이름) 10월 5일 → 시간 삼각김밥 → 물건 (이름) 커피 → 물건 (이름) 2개, 1잔 → 수량 주문했다 → 둘 사이의 관계

값들(김철수·삼각김밥·10월 5일)과 값 사이의 관계(주문했다)가 섞여 있습니다. 이 둘을 갈라내는 것이 데이터 모델링의 시작입니다.

나잘못 시작하면
주문표 ┌──────┬────────┬──────┬──────┬──────┐ │ 고객 │ 날짜 │ 상품 │ 수량 │ 가격 │ ├──────┼────────┼──────┼──────┼──────┤ │김철수│10-05 │삼각김밥│ 2 │1400 │ │김철수│10-05 │커피 │ 1 │1800 │ └──────┴────────┴──────┴──────┴──────┘ 한 번의 주문이 두 행으로 흩어짐

주문 하나가 여러 행에 흩어지고, 고객 이름과 상품 이름이 반복됩니다. 3편에서 본 중복이 여기서 다시 나타납니다.

02

개체와 속성Entity & Attribute

ERD의 두 재료입니다. 개체는 타입과 인스턴스로, 속성은 여섯 갈래로 나뉩니다.

1개체 타입과 개체 인스턴스

개체는 현실 세계에서 독립적으로 존재하는 것입니다. 개체 타입은 틀, 개체 인스턴스는 실제 값입니다.

개체 타입 : 고객 개체 인스턴스 ┌───────────┐ ┌─────────────────────┐ │ 고객 │ ────▶ │ 김철수 / 이영희 / 박민수 │ └───────────┘ └─────────────────────┘ (틀·설계도) (실제 데이터 행)

릴레이션으로 옮기면 개체 타입 = 테이블, 개체 인스턴스 = 튜플(행)입니다.

2속성의 여섯 갈래
속성뜻예ERD 표기
단순 속성더 나눌 수 없음나이, 성별타원
복합 속성여러 값으로 나뉨주소(시·구·동)큰 타원 + 작은 타원
단일값 속성값이 하나주민번호타원
다중값 속성값이 여러 개전화번호, 취미이중 타원
유도 속성다른 값에서 계산됨나이(생년월일), 총액점선 타원
키 속성개체를 유일하게 식별고객번호밑줄
3ERD 기호로 보기
40과 NULL값

두 값은 다릅니다. 0은 "값이 0"이고, NULL은 "값을 모르거나 해당 없음"입니다.

재고수량 = 0 → "품절" 이라는 사실을 아는 상태 재고수량 = NULL → "재고를 아직 세지 못함" 이라는 상태 전화번호 = NULL → "전화번호가 없는 고객" (해당 없음)
집계할 때 반드시 걸립니다 AVG(재고수량)은 NULL을 분모에서 제외합니다. 0을 NULL로 바꾸면 평균이 달라집니다.

03

관계와 관계의 유형Relationship

관계는 개체와 개체가 맺는 뜻 있는 연결입니다. 연결되는 개체의 수에 따라 세 가지로 나뉩니다.

1일대일 (1:1)

양쪽이 각각 하나씩만 연결됩니다.

사람 ──── 혼인증 ──── 사람 배우자 1명 ↔ 배우자 1명

실무에서는 같은 개체를 굳이 나눈 경우가 많습니다(보안 정보 분리 등).

2일대다 (1:N)

한쪽 하나가 다른 쪽 여러 개와 연결됩니다. 가장 흔한 관계입니다.

부서 ──── 소속 ──── 사원 1개 부서 ↔ N명 사원 (사원은 부서 하나에만)

고객–주문, 게시판–글, 카테고리–상품이 모두 1:N입니다.

3다대다 (N:M)

양쪽 모두 여러 개와 연결됩니다. 관계 자체에 속성이 생깁니다.

고객 ──── 구매 ──── 책 N명 고객 ↔ M권의 책 (구매일·수량은 관계의 속성)

릴레이션으로 옮길 때 별도 테이블이 필요합니다(다음 편).

4관계의 종류와 ERD 표기
5관계의 참여도와 차수
참여도전체 참여(모든 개체가 반드시 참여) / 부분 참여(일부만 참여)
차수관계에 참여하는 개체의 수 — 2개면 이항, 3개면 삼항
참여도 예 "모든 주문은 반드시 한 고객에 속한다" → 주문은 전체 참여
"고객은 주문이 없을 수도 있다" → 고객은 부분 참여
6관계도 속성을 가진다

관계는 연결만이 아니라 값을 가질 수 있습니다. 다대다 관계에서 특히 그렇습니다.

고객 ── 구매 ── 책 │ 관계의 속성 · 구매일 · 수량 · 결제금액

이 속성들을 어디에 둘지가 다음 편의 핵심 주제입니다.

04

논리적 데이터 모델Logical Data Models

개념 구조를 컴퓨터가 다룰 수 있는 형식으로 옮긴 것입니다. 세 가지 모델이 순서대로 등장했습니다.

1계층 데이터 모델

부모-자식 트리 구조입니다. 1:N 관계만 표현할 수 있습니다.

회사 ╱ ╲ 부서1 부서2 │ 사원1, 사원2

1편의 계층형 DBMS(IMS)와 짝을 이룹니다. 다대다를 표현할 수 없어 중복 저장이 생깁니다.

2네트워크 데이터 모델

그래프 구조로 다대다 관계까지 표현합니다. 레코드 사이에 여러 개의 링크를 둘 수 있습니다.

사원 ──▶ 부서 │ ╲ │ ╲──▶ 프로젝트 └──────▶ 스킬

표현력은 좋지만 구조가 복잡하고 물리 구조에 종속됩니다.

3관계 데이터 모델

데이터를 2차원 표(릴레이션)로 표현합니다. 단순하고 수학적 기반이 튼튼해 현재의 표준입니다.

고객(고객번호, 이름, 주소) 주문(주문번호, 고객번호, 날짜)

관계 사이의 연결은 값의 일치(외래키)로 표현합니다. 다음 편 전체가 이 모델입니다.

4세 모델 비교
항목계층 모델네트워크 모델관계 모델
구조트리그래프2차원 표
관계 표현1:N만1:N, N:M모두 (표로 변환)
검색 방법포인터 따라가기링크 따라가기값의 조건(SQL)
구조 변경어려움어려움비교적 쉬움
사용 편의낮음낮음높음

05

쇼핑몰 ERD 그려 보기Practice

배운 기호로 6편 전체에서 쓸 예제의 ERD를 완성합니다. 왼쪽은 개념 구조, 오른쪽은 그것을 표로 옮긴 모습입니다.

1개체 찾기 — 명사에 밑줄
"고객이 상품을 주문한다. 고객은 여러 번 주문할 수 있고, 한 주문에 여러 상품이 담긴다. 상품은 카테고리로 분류된다."
개체고객, 주문, 상품, 카테고리
관계고객─주문(1:N), 주문─상품(N:M), 카테고리─상품(1:N)
관계의 속성주문─상품의 수량·단가
2관계 유형 판정
문장관계근거
고객이 주문한다1:N한 고객이 여러 주문, 주문은 한 고객
주문에 상품이 담긴다N:M한 주문에 여러 상품, 한 상품이 여러 주문
상품이 분류된다1:N한 카테고리에 여러 상품, 상품은 한 카테고리
N:M은 반드시 쪼갭니다 주문─상품의 N:M은 order_item이라는 중간 개체로 나눠 두 개의 1:N으로 만듭니다. 그래야 수량·단가를 붙일 곳이 생깁니다.
3완성된 ERD
4개념 ERD → 논리 구조
고객(고객번호, 이름, 이메일, 연락처, 주소) 주문(주문번호, 고객번호, 주문일시, 상태) 주문상세(주문번호, 상품번호, 수량, 단가) 상품(상품번호, 이름, 카테고리번호, 가격, 재고) 카테고리(카테고리번호, 이름)

밑줄 친 것이 키입니다. 이 변환 규칙과 키의 종류는 다음 편에서 자세히 다룹니다.

5변환 규칙 요약
개념 구조릴레이션으로 옮기면
개체테이블 하나
1:N 관계N쪽 테이블에 1쪽의 키를 외래키로 추가
1:1 관계한쪽 테이블에 다른 쪽 키를 외래키로 추가(제약 UNIQUE)
N:M 관계관계를 별도 테이블로 만들고 양쪽 키를 외래키로
관계의 속성N:M이면 관계 테이블에, 1:N이면 N쪽 테이블에

  2. 프롬프트 채우기아래 [ ]를 채웁니다.
  3. ERD 받기개체·속성·관계와 다이어그램을 받습니다.
  4. 검증빠진 개체와 잘못된 관계 유형을 직접 확인합니다.
G3프롬프트 전체
# 역할
너는 데이터 모델링과 E-R 모델을 가르치는 설계 튜터다.

# 배경
나는 아래 업무 설명에서 데이터베이스 설계의 출발점이 될 ERD를 만들려고 한다.
- 업무 설명: [산문으로 붙여 넣기]
- 이 시스템의 사용자: [예: 고객, 상담원, 관리자]
- 지금 쓰는 문서·엑셀 양식: [있으면 붙여 넣기]
- 나중에 답하고 싶은 질문: [예: 지난달 카테고리별 매출은? 재구매율은?]

# 하고 싶은 일 (해당하는 번호만 남긴다)
A. 개체 추출: 명사 중에서 독립적으로 관리할 대상을 개체로 뽑고, 왜 그것이 개체인지 근거를 적는다.
B. 속성 분류: 각 개체의 속성을 단순/복합/단일값/다중값/유도/키 속성으로 분류한다.
C. 관계 도출: 개체 사이의 관계를 찾아 1:1 / 1:N / N:M 을 판정하고, 그 근거가 되는 문장을 인용한다.
D. 관계의 속성: 관계에 붙어야 하는 속성(수량·일자·금액 등)을 찾아 어디에 둘지 제안한다.
E. ERD 텍스트 표기: Mermaid erDiagram 문법으로 ERD를 그린다.
F. 논리 구조 변환: ERD를 릴레이션(테이블) 목록으로 옮기고, 각 테이블의 기본키 후보를 적는다.

# 반드시 지킬 것
1. 개체는 "여러 인스턴스가 있고 독립적으로 관리할 필요가 있는 것"만 뽑는다. 값의 목록(예: 성별 구분)은 개체가 아니라 코드다.
2. 다중값 속성은 그대로 두지 말고 별도 개체로 분리하는 안을 함께 제시한다.
3. 유도 속성(나이, 합계 등)은 저장하지 않는 것을 기본으로 하고, 저장이 필요한 경우 이유를 적는다.
4. N:M 관계는 반드시 중간 개체로 분해하고, 그 개체의 이름을 제안한다.
5. 모든 판정에 근거 문장을 인용한다. 근거가 없으면 "추정"이라고 표시한다.
6. 지어내지 않는다. 내가 준 설명에 없는 개체·속성을 임의로 추가하지 않는다.
7. 주석과 설명은 한국어로, 입문자도 따라올 수 있게 쓴다.

G3전체 코드
USE shop;
SET FOREIGN_KEY_CHECKS = 0;
DROP TABLE IF EXISTS order_item, orders, product, category, customer;
SET FOREIGN_KEY_CHECKS = 1;

-- [1] 1쪽 개체들 먼저
CREATE TABLE category (
  category_id INT PRIMARY KEY AUTO_INCREMENT,
  name        VARCHAR(40) NOT NULL UNIQUE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE customer (
  customer_id INT PRIMARY KEY AUTO_INCREMENT,
  name        VARCHAR(30) NOT NULL,
  email       VARCHAR(120) NOT NULL UNIQUE,
  addr        VARCHAR(200)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- [2] 1:N — N쪽(product)에 1쪽(category)의 키를 외래키로
CREATE TABLE product (
  product_id  INT PRIMARY KEY AUTO_INCREMENT,
  name        VARCHAR(80) NOT NULL,
  category_id INT,                                  -- FK
  price       DECIMAL(10,2) NOT NULL,
  stock       INT NOT NULL DEFAULT 0,
  CONSTRAINT fk_product_category FOREIGN KEY (category_id)
    REFERENCES category(category_id) ON DELETE SET NULL
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE orders (
  order_id    INT PRIMARY KEY AUTO_INCREMENT,
  customer_id INT NOT NULL,                         -- FK (1:N)
  ordered_at  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  status      VARCHAR(10) NOT NULL DEFAULT '신규',
  CONSTRAINT fk_orders_customer FOREIGN KEY (customer_id)
    REFERENCES customer(customer_id) ON DELETE RESTRICT
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- [3] N:M 분해 — 관계를 개체로 만든다. 수량·단가는 여기에 붙는다
CREATE TABLE order_item (
  order_id   INT NOT NULL,
  product_id INT NOT NULL,
  quantity   INT NOT NULL CHECK (quantity > 0),
  unit_price DECIMAL(10,2) NOT NULL,      -- 주문 시점의 가격 (나중에 바뀌어도 보존)
  PRIMARY KEY (order_id, product_id),     -- 복합 기본키: 같은 주문에 같은 상품 중복 금지
  CONSTRAINT fk_oi_order   FOREIGN KEY (order_id)   REFERENCES orders(order_id)  ON DELETE CASCADE,
  CONSTRAINT fk_oi_product FOREIGN KEY (product_id) REFERENCES product(product_id) ON DELETE RESTRICT
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 관계를 따라가 보기: 1:N 을 조인으로
SELECT o.order_id, c.name AS 고객, o.ordered_at
FROM orders o JOIN customer c ON c.customer_id = o.customer_id;

-- N:M 을 양쪽에서 조인으로
SELECT o.order_id, p.name AS 상품, i.quantity, i.unit_price,
       i.quantity * i.unit_price AS 금액
FROM order_item i
JOIN orders  o ON o.order_id  = i.order_id
JOIN product p ON p.product_id = i.product_id;
G4라인별 해설
줄설명
생성 순서1쪽 개체(category·customer)를 먼저 만들어야 N쪽이 참조할 수 있습니다.
ON DELETE SET NULL카테고리가 지워져도 상품은 남고 분류만 비워집니다. 관계의 의미에 따라 정책을 고릅니다.
ON DELETE RESTRICT주문이 있는 고객은 삭제 불가 — 실수로 이력이 사라지는 것을 막습니다.
PRIMARY KEY (order_id, product_id)N:M을 분해한 테이블의 복합 기본키. 같은 주문에 같은 상품이 두 번 들어가는 것을 막습니다.
unit_price 저장상품 가격이 나중에 바뀌어도 주문 당시 가격을 보존합니다. 유도 속성을 저장하지 않는 원칙의 예외이며, 이유가 명확합니다.
ON DELETE CASCADE주문이 지워지면 그 상세도 함께 지웁니다. 고아 레코드를 막습니다.

오류원인해결
ERROR 1215참조 열 타입 불일치양쪽을 INT로 통일합니다.
ERROR 1062 (복합키 중복)같은 주문·상품을 두 번 넣음정상 동작입니다. ON DUPLICATE KEY UPDATE quantity = quantity + VALUES(quantity)로 수량을 합칩니다.
ERROR 1451 (삭제 불가)자식 행이 있는 부모 삭제정책을 CASCADE로 바꾸거나 자식부터 정리합니다.

G2실행 순서
  1. ERD 작성Mermaid 문자열로 씁니다.
  2. 검증관계 문법이 맞는지 확인합니다.
  3. 파일로 저장깃에 넣을 수 있게 저장합니다.
  4. DB와 대조실제 테이블 목록과 비교합니다.
G3전체 코드
# -*- coding: utf-8 -*-
"""5주차 실습 — ERD 텍스트 관리와 DB 대조"""
import os, re
import pandas as pd
from sqlalchemy import create_engine

# [1] ERD를 텍스트로 (Mermaid) — 깃으로 버전 관리할 수 있다
ERD = """
erDiagram
    CATEGORY ||--o{ PRODUCT     : "분류한다"
    CUSTOMER ||--o{ ORDERS      : "주문한다"
    ORDERS   ||--|{ ORDER_ITEM  : "담는다"
    PRODUCT  ||--o{ ORDER_ITEM  : "담긴다"

    CATEGORY { int category_id PK
               string name }
    CUSTOMER { int customer_id PK
               string name
               string email }
    PRODUCT  { int product_id PK
               int category_id FK
               string name
               numeric price }
    ORDERS   { int order_id PK
               int customer_id FK
               datetime ordered_at }
    ORDER_ITEM { int order_id PK,FK
                 int product_id PK,FK
                 int quantity
                 numeric unit_price }
"""
open("erd.mmd", "w", encoding="utf-8").write(ERD)
print("erd.mmd 저장 완료")

# [2] 텍스트에서 관계와 카디널리티 뽑아 검사
rels = re.findall(r"^\s*(\w+)\s+(\|\|--o\{|\|\|--\| \{|\}o--o\{|\|\|--\|\{)\s+(\w+)", ERD, re.M)
print("관계 목록:")
for a, card, b in rels:
    kind = "1:N" if "o{" in card else ("1:1" if card.count("|") == 4 else "N:M")
    print(f"  {a:10s} {kind:4s} {b}")

# [3] 다대다(N:M)가 남아 있는지 점검 — 남아 있으면 분해가 빠진 것
nm = [r for r in rels if "}o--o{" in r[1]]
print("분해되지 않은 N:M:", nm if nm else "없음 (정상)")

# [4] 실제 DB와 대조 — ERD에 있는데 DB에 없는 테이블 찾기
engine = create_engine(os.environ.get(
    "SHOP_DB_URL",
    "mysql+mysqlconnector://root:비밀번호@127.0.0.1:3306/shop?charset=utf8mb4"))

db_tables = pd.read_sql("""
    SELECT TABLE_NAME FROM information_schema.TABLES
    WHERE TABLE_SCHEMA='shop' AND TABLE_TYPE='BASE TABLE'
""", engine)["TABLE_NAME"].str.lower().tolist()

erd_tables = [m.lower() for m in re.findall(r"^\s{4}(\w+)\s*\{", ERD, re.M)]
print("ERD에만 있고 DB에 없음:", sorted(set(erd_tables) - set(db_tables)))
print("DB에만 있고 ERD에 없음:", sorted(set(db_tables) - set(erd_tables)))

# [5] 외래키가 실제로 걸려 있는지 확인 — ERD의 선이 DB에도 있는가
fks = pd.read_sql("""
    SELECT TABLE_NAME, COLUMN_NAME, REFERENCED_TABLE_NAME, REFERENCED_COLUMN_NAME
    FROM information_schema.KEY_COLUMN_USAGE
    WHERE TABLE_SCHEMA='shop' AND REFERENCED_TABLE_NAME IS NOT NULL
""", engine)
print(fks.to_string(index=False))
G4라인별 해설

개체와 속성

개체 (Entity)

비유서류함에 따로 보관할 만한 것. 이름표를 붙일 수 있고 여러 개가 있습니다.

뜻현실 세계에서 독립적으로 존재하는 대상. 개체 타입(틀)과 개체 인스턴스(실제 값)로 나뉩니다.

속성 (Attribute)

비유인물 카드에 적는 항목 — 이름, 나이, 주소.

뜻개체가 가지는 특성. 단순·복합·단일값·다중값·유도·키 속성으로 나뉩니다.

복합 속성

비유"주소"라고 적었지만 실제로는 시·구·동 세 칸입니다.

뜻여러 개의 단순 속성으로 나눌 수 있는 속성.

유도 속성

비유계산으로 나오는 값. 적어 두지 않아도 언제든 다시 계산할 수 있습니다.

뜻다른 속성 값에서 계산되는 속성(나이, 합계). ERD에서 점선 타원으로 표기합니다.

NULL값

비유빈칸과 0은 다릅니다. "모른다"와 "없다"도 다릅니다.

뜻값을 모르거나 적합한 값이 없는 경우를 표시하는 특별한 값.

관계와 모델

관계 (Relationship)

비유두 서류함 사이를 잇는 실. 그 실에 이름표와 값이 붙을 수 있습니다.

뜻개체와 개체 사이의 뜻 있는 연결. 1:1, 1:N, N:M으로 나뉘고 자체 속성을 가질 수 있습니다.

관계 유형 (카디널리티)

비유한 사람이 여러 장을 가질 수 있는지, 서로 여러 개인지.

뜻연결되는 개체 인스턴스의 수 관계. 1:1 / 1:N / N:M.

참여도

비유반드시 있어야 하는 참가자인지, 있어도 되고 없어도 되는지.

뜻전체 참여(모든 개체가 반드시 참여)와 부분 참여(일부만 참여)로 구분합니다.

ERD

비유건물을 짓기 전의 배치도. 아직 벽은 없지만 어디에 무엇이 놓일지 정해져 있습니다.

뜻개체-관계 다이어그램. 개체·속성·관계를 그림으로 표현한 개념적 구조.

L12편 실습 — 파이썬의 데이터 구조로 같은 고객 데이터 표현하기

모범 답안 요점 — 같은 고객 한 명을 네 가지 구조로 옮겨 보고, 각 구조가 무엇을 흉내 내는지 말할 수 있어야 합니다.
  • 튜플 — (고객번호, 이름, 이메일)처럼 순서가 고정된 한 건의 레코드. 한 번 만들면 바뀌지 않으므로 행 하나에 대응합니다.
  • 리스트 — 튜플들을 담은 목록. 곧 테이블(튜플의 집합)이며, 순서가 있다는 점이 릴레이션의 '튜플 무순서'와 다릅니다.
  • 딕셔너리 — {"이름": "김철수", "이메일": "a@shop.com"}처럼 값에 이름표(키)가 붙은 형태. 데이터 안에 구조 설명이 들어 있으므로 반정형 데이터에 해당합니다.
  • 집합 — 중복을 자동으로 제거합니다. 고객번호 목록에서 중복을 없애는 작업은 곧 키의 유일성을 확인하는 일입니다.
  • pandas DataFrame — 열 이름과 값이 2차원 표로 정리되므로 릴레이션과 가장 가깝습니다. 열 이름 = 속성, 인덱스 = 튜플.
채점 포인트 — 네 구조를 나열하는 것만으로는 부족합니다. "딕셔너리는 이름표를 스스로 들고 있어서 반정형, DataFrame은 2차원 표라 릴레이션에 가깝다"처럼 대응 관계를 말하면 만점입니다.

L25편 실습 — 쇼핑몰 ERD를 릴레이션으로 옮기기

모범 답안 요점 — 개체는 테이블로, 관계는 N쪽의 외래키 또는 별도 테이블로 옮깁니다.
  • category(카테고리번호 PK, 이름)
  • customer(고객번호 PK, 이름, 이메일, 주소)
  • product(상품번호 PK, 이름, 가격, 카테고리번호 FK → category) — 1:N이므로 N쪽(product)에 1쪽의 키를 넣습니다.
  • orders(주문번호 PK, 고객번호 FK → customer, 주문일, 상태) — 한 고객이 여러 주문을 하므로 N쪽은 orders입니다.
  • order_item(주문번호 + 상품번호 PK, 수량, 단가) — 주문과 상품은 N:M이라 별도 테이블로 분해하고, 수량·단가 같은 관계의 속성을 이 테이블에 둡니다.
채점 포인트 — ① N:M을 order_item으로 분해했는가 ② 외래키 방향(N쪽에 FK)을 맞게 잡았는가 ③ 수량을 상품 테이블이 아니라 order_item에 두었는가. 이 세 가지가 핵심입니다.

L36편 실습 — 적재 전 키·무결성 위반 점검

모범 답안 요점 — 데이터를 넣기 전에 아래 순서로 점검하고, 위반은 정책을 정해서 고칩니다.
  • 개체 무결성 — 기본키에 NULL이나 중복이 있는지. 고객번호가 비어 있으면 그 행은 개체로 성립하지 않습니다.
  • 참조 무결성 — orders.고객번호가 customer에 없는 값을 가리키는지(고아 레코드). 있으면 그 주문은 임시 고객을 만들지, 적재를 보류할지 정해야 합니다.
  • 도메인 제약 — 가격에 음수, 이메일에 형식 위반 값이 들어오는지.
  • 순환 참조 — 서로를 참조하는 두 테이블은 삽입 순서가 얽히므로 지연(deferrable) 제약으로 검사를 커밋 시점까지 미룹니다.
채점 포인트 — 위반을 찾는 것보다 "어느 정책이 업무에 맞는가"를 근거와 함께 정하는 것이 이 실습의 목표입니다. 정책 없이 "삭제하면 됩니다"라고만 답하면 절반 점수입니다.

L47편 실습 — RPG 데이터베이스 설계 10단계와 인덱스 효과

모범 답안 요점 — 파일 시스템의 한계 인식 → DBMS 도입 → 3단계 구조 → 개체 도출 → 관계 정리 → 인덱스·운영 순으로 답이 이어져야 합니다.
  • 개체 — game_character, character_stat, item, inventory, battle_log. 캐릭터와 아이템은 N:M이므로 inventory(중간 테이블)로 분해하고 수량을 그곳에 둡니다.
  • 캐릭터와 스탯 분리 — 자주 조회되는 기본 정보와 자주 바뀌지 않는 상세 스탯을 나눠 관리하는 성능 최적화 목적입니다. 레벨업 시 스탯 갱신은 트랜잭션으로 묶습니다.
  • 인덱스 — 활성 퀘스트 조회에는 player_id + status 복합 인덱스를 씁니다. 선행/후행 관계는 그래프로, 선택 기록은 JSON으로 관리합니다.
  • 장애와 개선 — 신규 서버 오픈 당일 동시접속 5만 명 상황에서 인벤토리 조회 지연으로 서비스가 마비되었고, 인덱스 추가와 조회 로직 개선으로 응답시간이 3초 → 0.1초로 줄었습니다.
  • 대규모 로그 — battle_log는 양이 계속 늘어나므로 기간별 파티셔닝으로 관리합니다.
  • 회고 — "가장 중요한 것은 미래의 확장성." 업데이트를 견디는 유연한 구조가 결론입니다.
채점 포인트 — 표를 몇 개 만들었는지보다 관계를 어떻게 풀었는지(N:M 분해, FK 방향)와 왜 그 인덱스를 골랐는지를 설명했는지가 점수의 대부분입니다.

수업 활용 팁Teaching Notes

여섯 편을 한 학기 흐름에 맞춰 쓰는 방법입니다.

A차시 배분
  • 2편 + 3편 — 데이터·정보의 구분과 DBMS의 등장 (2차시)
  • 4편 — 3단계 구조와 데이터 독립성 (1차시)
  • 5편 + 6편 — 모델링과 관계 모델, 쇼핑몰 ERD 실습 (2차시)
  • 7편 — RPG 사례로 전체 복습 (1~2차시)
B오답이 몰리는 지점
  • 데이터 ↔ 정보의 경계 — '평균 구매액'처럼 계산 결과인지로 판단하게 지도
  • 차수 ↔ 카디널리티 — "차수=열, 카디널리티=행"으로 고정
  • 논리적 ↔ 물리적 데이터 독립성 — 어느 스키마 사이의 이야기인지 확인
  • 1:N 변환 방향 — 외래키는 항상 N쪽
C코드 가이드 활용

각 편의 코드 가이드 탭에는 MySQL · PostgreSQL · 파이썬 예제가 함께 있습니다. 같은 설계를 세 도구로 옮겨 보게 하면 방언 차이(자료형, AUTO_INCREMENT ↔ SERIAL)와 개념의 공통 뼈대가 동시에 남습니다.

1초기 단계의 문제점
데이터 중복캐릭터·아이템 정보가 여러 파일에 중복 저장
데이터 종속성속성 변경 시 연관 파일 모두 수정 필요
동시 접근 불가개발자 간 동시 작업 시 충돌 발생
확장성 부족신규 기능 추가 시 전체 구조 수정 필요
개발자의 고민

"프로젝트가 커지면서 파일이 너무 많아졌어요. 최신 버전 관리도 어렵고 팀원들과 작업 시 충돌이 계속됩니다."

2프로젝트 리더의 결정
프로젝트 리더

"이 방식으로는 용사의 전설에 필요한 수백 개의 아이템과 퀘스트를 관리할 수 없습니다. 데이터베이스 시스템이 필요합니다."

데이터 일관성캐릭터·아이템 정보 중복 문제 해결
동시 접근성개발자들의 동시 작업 지원
복구 체계게임 데이터 손상 방지 시스템
기술 검토 결과 · 팀 피드백

"용사의 전설에서 필요한 복잡한 캐릭터 성장 시스템을 위해 관계형 DB 도입이 필수적입니다." → "DBMS 도입으로 개발 속도가 30% 향상되었습니다."

3DBMS의 3대 기능과 실제 활용
정의Define · DDL

RPG 게임의 세계관을 구축하는 기초 작업입니다. 캐릭터·아이템·스킬·NPC 등의 데이터 구조를 정의하고, 복잡한 캐릭터-직업-스킬 간의 관계를 설정합니다.

조작Manipulate · DML

게임 진행에 따른 실시간 데이터 관리입니다. 레벨업·스탯 변화·퀘스트 진행 등 상태를 업데이트하고, 아이템 획득/거래/사용에 따른 인벤토리를 변경합니다.

제어Control · DCL

게임 데이터 안전성과 일관성을 보장합니다. 접근 권한을 관리하고(개발/QA/운영팀), 동시 작업 시 충돌을 방지하며 데이터 무결성을 유지합니다.

영웅전설 개발팀의 실제 활용 🔷 캐릭터 성장 시스템 — 레벨업에 따른 스탯 자동 계산과 직업별 차등 적용 로직을 DB 프로시저로 구현
🔷 전투 밸런싱 — 몬스터/캐릭터 데이터 분석을 통해 게임 난이도를 조절하고, 쿼리로 데이터 검증
🔷 다중 개발자 협업 — 트랜잭션 관리로 여러 개발자가 동시에 수정해도 충돌 없음
🔷 컨텐츠 확장 — 새로운 DLC 추가 시 기존 구조 변경 없이 데이터만 추가

"DBMS 도입 후 게임 데이터 관리 시간이 60% 감소했고, 개발자들은 실제 게임플레이 개선에 더 집중할 수 있었습니다." — 프로젝트 리드

4실무적 평가 — 이점과 과제
개발팀에게 주는 이점
  • 데이터 통합 관리 — 캐릭터·아이템·스킬 데이터의 중복 방지
  • 시스템 확장성 — DLC·신규 퀘스트·아이템 추가가 용이
  • 계정 보안 — 플레이어 데이터 안전성 확보
  • 시스템 복구 — 서버 장애 발생 시 데이터 롤백 가능
  • 동시 접속 처리 — 다중 서버에서 데이터 일관성 유지
개발팀이 마주하는 과제
  • 개발 비용 증가 — DB 전문 인력과 고성능 서버 인프라 필요
  • 백업/유지보수 — 정기적 백업과 DB 최적화 작업 필수
  • 시스템 의존성 — DB 장애 시 전체 게임 서비스 중단 가능성
  • 초기 설계의 중요성 — 라이브 서비스 후 스키마 변경의 어려움
개발팀 실무 인사이트 "영웅전설 같은 대규모 RPG 개발에서 DBMS는 선택이 아닌 필수입니다. 특히 복잡한 퀘스트 시스템과 NPC 관리에 효율성을 크게 높여줍니다."
→ 일본식 RPG 개발에서는 게임 규모와 서비스 계획에 따라 적합한 DB 솔루션을 선택해야 합니다.

G3프롬프트 전체
# 역할
너는 대규모 서비스(게임/커머스)의 데이터베이스 설계를 리뷰하는 실무 설계자다.

# 배경
나는 아래 도메인의 데이터베이스를 설계하려고 한다.
- 도메인: [예: 턴제 RPG — 캐릭터, 아이템, 인벤토리, 전투 로그, 퀘스트 진행]
- 핵심 규칙:
  [예]
  · 캐릭터는 직업과 레벨을 가지며, 레벨업 시 스탯이 재계산된다
  · 아이템은 유형과 희귀도가 있고, 캐릭터는 여러 아이템을 여러 개 가질 수 있다
  · 퀘스트는 선행 퀘스트가 있으며, 플레이어의 선택에 따라 분기된다
  · 전투 로그는 초당 수백 건이 쌓인다
- 예상 규모: 동시접속 [ ], 캐릭터 [ ]명, 로그 하루 [ ]건
- 자주 하는 조회: [예: 캐릭터 인벤토리 조회, 활성 퀘스트 목록, 서버별 랭킹]
- 쓰는 DBMS: [MySQL / PostgreSQL]

# 하고 싶은 일 (해당하는 번호만 남긴다)
A. 스키마 설계: 테이블·열·타입·키·제약을 포함한 전체 DDL을 만든다.
B. 관계 검증: 모든 다대다 관계가 중간 테이블로 분해되었는지 확인하고, 누락분을 고친다.
C. 인덱스 전략: 자주 하는 조회를 기준으로 인덱스를 설계하고, 각 인덱스의 근거를 적는다.
D. 정규화 판단: 어디를 정규화하고 어디를 비정규화할지 결정하고 이유를 적는다.
E. 성능 측정: 인덱스 유무에 따른 실행계획과 예상 비용 차이를 설명하고, 측정용 SQL을 만든다.
F. 확장성 리뷰: 6개월 뒤 기능이 추가될 때 스키마를 고치지 않아도 되는 부분과 고쳐야 하는 부분을 나눈다.

# 반드시 지킬 것
1. 모든 테이블에 기본키를 둔다. 자연키가 부적합하면 대리키를 쓰고 이유를 적는다.
2. 다대다 관계는 반드시 중간 테이블로 분해한다.
3. 자주 바뀌는 값(현재 HP, 진행 단계)과 거의 안 바뀌는 값(직업, 아이템 유형)을 분리한다.
4. 로그처럼 쓰기가 폭발적인 테이블은 비정규화를 검토하고, 그 이유를 적는다.
5. 인덱스는 "어떤 쿼리를 위해" 만드는지 반드시 적는다. 근거 없는 인덱스는 만들지 않는다.
6. 성능 수치를 말할 때는 측정 방법을 함께 적는다. 측정하지 않은 수치를 만들지 않는다.
7. 지어내지 않는다. 내가 준 규칙에 없는 기능을 임의로 추가하지 않는다.
8. 주석과 설명은 한국어로, 입문자도 따라올 수 있게 쓴다.

# 답변 형식
1. 한 줄 요약 (테이블 수, 가장 위험한 지점)
2. 전체 DDL (스키마 → 테이블 → 제약 → 인덱스 순서)
3. 조회별 인덱스 근거 표 (조회 / 사용 인덱스 / 근거 / 예상 효과)
4. 정규화·비정규화 결정 표
5. 확장성 리뷰 (고치지 않아도 되는 부분 / 고쳐야 하는 부분)
6. 측정용 SQL과 읽는 법

G3전체 코드
CREATE DATABASE IF NOT EXISTS game CHARACTER SET utf8mb4;
USE game;

DROP TABLE IF EXISTS battle_log, inventory, item, character_stat, game_character, job;

CREATE TABLE job (
  job_id   TINYINT PRIMARY KEY,
  job_name VARCHAR(20) NOT NULL UNIQUE      -- 마법검사, 현자 …
);

CREATE TABLE game_character (
  character_id INT PRIMARY KEY AUTO_INCREMENT,
  name         VARCHAR(50) NOT NULL,
  job_id       TINYINT NOT NULL,
  level        SMALLINT NOT NULL DEFAULT 1,
  exp          INT NOT NULL DEFAULT 0,
  created_at   DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  CONSTRAINT fk_char_job FOREIGN KEY (job_id) REFERENCES job(job_id),
  CONSTRAINT ck_char_level CHECK (level BETWEEN 1 AND 99)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 1:1 — 스탯은 별도 테이블 (자주 바뀌는 값)
CREATE TABLE character_stat (
  character_id INT PRIMARY KEY,
  strength     SMALLINT NOT NULL DEFAULT 10,
  intelligence SMALLINT NOT NULL DEFAULT 10,
  dexterity    SMALLINT NOT NULL DEFAULT 10,
  vitality     SMALLINT NOT NULL DEFAULT 10,
  CONSTRAINT fk_stat_char FOREIGN KEY (character_id)
    REFERENCES game_character(character_id) ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE item (
  item_id  INT PRIMARY KEY AUTO_INCREMENT,
  name     VARCHAR(50) NOT NULL,
  type_id  TINYINT NOT NULL,      -- 유형 (FK → item_type)
  rarity   TINYINT NOT NULL,      -- 희귀도 1~5
  CONSTRAINT ck_item_rarity CHECK (rarity BETWEEN 1 AND 5)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- N:M — 인벤토리가 중간 테이블
CREATE TABLE inventory (
  character_id INT NOT NULL,
  item_id      INT NOT NULL,
  quantity     INT NOT NULL DEFAULT 1,
  PRIMARY KEY (character_id, item_id),
  CONSTRAINT fk_inv_char FOREIGN KEY (character_id) REFERENCES game_character(character_id) ON DELETE CASCADE,
  CONSTRAINT fk_inv_item FOREIGN KEY (item_id)      REFERENCES item(item_id) ON DELETE RESTRICT,
  CONSTRAINT ck_inv_qty  CHECK (quantity > 0)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 쓰기 폭발 테이블 — 비정규화 (캐릭터 이름을 함께 저장해 조인 제거)
CREATE TABLE battle_log (
  log_id      BIGINT PRIMARY KEY AUTO_INCREMENT,
  battle_id   INT NOT NULL,
  character_id INT NOT NULL,
  action_type VARCHAR(20) NOT NULL,      -- 공격/스킬/방어
  damage      INT NOT NULL DEFAULT 0,
  created_at  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- ── 대량 데이터 생성 (재귀 CTE) ───────────────────────
INSERT INTO job VALUES (1,'마법검사'),(2,'현자'),(3,'기사');
INSERT INTO game_character (name, job_id, level)
WITH RECURSIVE seq(n) AS (SELECT 1 UNION ALL SELECT n+1 FROM seq WHERE n < 20000)
SELECT CONCAT('용사', n), 1 + (n % 3), 1 + (n % 99) FROM seq;
INSERT INTO item (name, type_id, rarity)
WITH RECURSIVE seq(n) AS (SELECT 1 UNION ALL SELECT n+1 FROM seq WHERE n < 2000)
SELECT CONCAT('아이템', n), 1 + (n % 10), 1 + (n % 5) FROM seq;
INSERT INTO inventory (character_id, item_id, quantity)
WITH RECURSIVE seq(n) AS (SELECT 1 UNION ALL SELECT n+1 FROM seq WHERE n < 60000)
SELECT 1 + (n % 20000), 1 + (n % 2000), 1 + (n % 9) FROM seq;
INSERT INTO battle_log (battle_id, character_id, action_type, damage)
WITH RECURSIVE seq(n) AS (SELECT 1 UNION ALL SELECT n+1 FROM seq WHERE n < 200000)
SELECT 1 + (n % 5000), 1 + (n % 20000), IF(n%3=0,'스킬','공격'), n % 900 FROM seq;

# -*- coding: utf-8 -*-
"""7주차 실습 — 인덱스 효과 측정과 기록"""
import os, time, statistics
import pandas as pd
from sqlalchemy import create_engine, text

engine = create_engine(os.environ.get(
    "GAME_DB_URL",
    "mysql+mysqlconnector://root:비밀번호@127.0.0.1:3306/game?charset=utf8mb4"))

QUERY = """
SELECT i.item_id, it.name, i.quantity
FROM inventory i JOIN item it ON it.item_id = i.item_id
WHERE i.character_id = :cid
"""

def measure(engine, sql, params, repeat=5):
    """같은 쿼리를 repeat회 실행해 중앙값과 최소값을 돌려준다."""
    times = []
    with engine.connect() as con:
        for _ in range(repeat):
            t0 = time.perf_counter()
            con.execute(text(sql), params).fetchall()
            times.append((time.perf_counter() - t0) * 1000)   # ms
    return {"중앙값_ms": round(statistics.median(times), 3),
            "최소_ms":   round(min(times), 3),
            "표준편차":  round(statistics.pstdev(times), 3)}

def index_exists(engine, table, index_name):
    q = """SELECT COUNT(*) FROM information_schema.STATISTICS
           WHERE TABLE_SCHEMA = DATABASE() AND TABLE_NAME = :t AND INDEX_NAME = :i"""
    with engine.connect() as con:
        return con.execute(text(q), {"t": table, "i": index_name}).scalar() > 0

CID = 12345
result = {}

# [1] 인덱스 제거 상태에서 측정
with engine.begin() as con:
    if index_exists(engine, "inventory", "idx_inv_char"):
        con.execute(text("DROP INDEX idx_inv_char ON inventory"))
result["인덱스 없음"] = measure(engine, QUERY, {"cid": CID})

# [2] 인덱스 생성 후 측정
with engine.begin() as con:
    con.execute(text("CREATE INDEX idx_inv_char ON inventory(character_id)"))
result["인덱스 있음"] = measure(engine, QUERY, {"cid": CID})

# [3] 실행계획 수집 — 풀 스캔이 사라졌는지 확인
with engine.connect() as con:
    plan = con.execute(text("EXPLAIN " + QUERY), {"cid": CID}).fetchall()
plan_txt = "\n".join(str(r[0]) for r in plan)
print(plan_txt)

# [4] 기록
df = pd.DataFrame(result).T
df["개선배수"] = (df.loc["인덱스 없음", "중앙값_ms"] / df["중앙값_ms"]).round(2)
print(df)
df.to_csv("index_benchmark.csv", encoding="utf-8-sig")
print("index_benchmark.csv 저장 완료")

# [5] 판단 — 인덱스를 유지할 가치가 있는가
before = df.loc["인덱스 없음", "중앙값_ms"]
after  = df.loc["인덱스 있음", "중앙값_ms"]
if after < before * 0.7:
    print(f"유지 권장: {before:.1f}ms → {after:.1f}ms ({before/after:.1f}배 개선)")
else:
    print("효과 미미: 인덱스 유지 비용(쓰기 지연·저장공간)을 재검토하세요")

실무 설계

인덱스

비유책 뒤의 찾아보기. 본문을 다 넘기지 않고 바로 그 쪽으로 갑니다. 대신 책이 조금 두꺼워집니다.

뜻특정 열의 값을 빠르게 찾기 위한 별도 자료 구조. 조회는 빨라지고 쓰기·저장공간은 늘어납니다.

복합 인덱스

비유"성+이름" 순으로 정렬된 명부. 성만으로도 찾을 수 있지만 이름만으로는 못 찾습니다.

뜻두 개 이상의 열을 묶은 인덱스. 열 순서가 성능을 좌우합니다.

카디널리티 (선택도)

비유값의 종류가 많은 열일수록 잘 걸러집니다. "성별"보다 "주민번호"가 훨씬 잘 걸러집니다.

뜻열에 들어 있는 서로 다른 값의 개수. 인덱스 열 순서를 정할 때 기준이 됩니다.

비정규화

비유자주 쓰는 값을 손님이 보는 자리에 미리 놓아 두기. 정리는 덜 됐지만 빠릅니다.

뜻성능을 위해 의도적으로 중복을 남기는 설계. 이유를 반드시 기록해야 합니다.

샤딩

비유한 창고가 꽉 차서 월드별로 창고를 나누는 것.

뜻데이터를 여러 서버에 나눠 저장해 대규모 동시접속을 처리하는 전략.

파티셔닝

비유한 장부를 월별 권으로 나누기. 10월 자료를 볼 때 9월 권은 열지 않습니다.

뜻큰 테이블을 기간·범위 등으로 나눠 관리하는 기법. 조회 범위를 좁혀 성능을 올립니다.

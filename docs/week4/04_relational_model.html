일곱 개의 낱말만 정확히 잡으면 나머지는 따라옵니다.

1릴레이션 · 속성 · 튜플

3도메인

속성 하나가 가질 수 있는 모든 값의 집합입니다. 모든 가능한 값을 나열하기 어렵기 때문에 속성의 특성을 고려한 데이터 타입으로 정의합니다.

고객등급 속성의 도메인 나열식 : { 'VIP', '일반', '휴면' } 타입식 : VARCHAR(10) + CHECK (grade IN ('VIP','일반','휴면'))
도메인을 정하는 이유 데이터가 가질 수 있는 값의 범위를 알기 때문에 잘못된 연산을 예방할 수 있습니다. 나이 도메인에 음수가 들어오지 못하게 막는 것이 그 예입니다.
4NULL값 · 차수 · 카디널리티
NULL값특정 튜플의 속성 값을 모르거나 적합한 값이 없는 경우에 사용. 특정 속성에 해당하는 값이 없다는 의미
차수하나의 릴레이션에서 속성의 전체 개수 (열의 수)
카디널리티하나의 릴레이션에서 튜플의 전체 개수 (행의 수)
카디널리티는 자주 바뀝니다 차수는 설계로 정해지지만 카디널리티는 데이터가 쌓이며 계속 변합니다. 성능 설계에서 "카디널리티가 높다/낮다"는 말이 자주 나오는 이유입니다.

스키마는 내연적(intension), 인스턴스는 외연적(extension)이라고도 합니다. 앞 편의 개념 스키마/개체 인스턴스와 같은 구도입니다.

6데이터베이스는 여러 릴레이션으로

데이터베이스는 복수의 릴레이션으로 구성됩니다. 예를 들어 쇼핑몰은 고객·상품·주문 릴레이션으로 구성됩니다.

shop 데이터베이스 ├── 고객 (고객번호, 이름, 이메일, 주소) ├── 상품 (상품번호, 이름, 카테고리번호, 가격) └── 주문 (주문번호, 고객번호, 주문일시, 상태)
7릴레이션의 네 가지 특징
  1. 튜플의 유일성하나의 릴레이션에는 동일한 튜플이 존재할 수 없다
  2. 튜플의 무순서하나의 릴레이션에서 튜플 사이의 순서는 무의미하다
  3. 속성의 무순서하나의 릴레이션에서 속성 사이의 순서는 무의미하다
  4. 속성의 원자성속성 값으로 원자 값만 사용할 수 있다
원자성이 깨지면 전화번호 = '010-1111, 010-2222'처럼 한 칸에 두 값을 넣으면, "010-2222를 가진 고객"을 찾을 수 없습니다. 그래서 다중값 속성은 별도 테이블로 분리합니다.

키의 종류Keys

키는 관계 데이터 모델에서 중요한 제약조건을 정의합니다. 다섯 종류를 포함관계로 이해하면 한 번에 정리됩니다.

1다섯 키의 포함 관계
2다섯 키 한눈에
키조건예
슈퍼키유일성만 만족고객번호 / 이메일 / (이름+이메일)
후보키유일성 + 최소성고객번호, 이메일

유일성 vs 최소성 유일성 — 튜플을 하나로 구별할 수 있다.
최소성 — 그 안에서 속성을 하나라도 빼면 구별하지 못한다. (이름+이메일)은 유일하지만 최소가 아닙니다. 이메일만으로도 구별되기 때문입니다.
3기본키 선택의 세 가지 기준
  1. NULL 값을 가질 수 있는 속성이 포함된 후보키는 부적합값이 없을 수도 있는 속성은 식별자로 쓸 수 없습니다.
  2. 값이 자주 변경될 수 있는 속성이 포함된 후보키는 부적합기본키가 바뀌면 참조하는 모든 행이 영향을 받습니다.
  3. 단순한 후보키를 기본키로 선택속성이 적고 짧은 쪽이 인덱스·조인에서 유리합니다.
고객 릴레이션의 후보키 두 개 ① 이메일 — 변경될 수 있음 (회사 이직 등) ✗ ② 고객번호 — 자동 증가, 변하지 않음 ✓ ← 기본키 대체키 : 이메일 (UNIQUE 제약으로 유지)
4외래키의 정의
외래키 : 어떤 릴레이션에 포함된 속성 또는 속성집합이 다른 릴레이션의 기본키가 되는 키
고객 릴레이션 주문 릴레이션 ┌──────────┬──────┐ ┌──────────┬──────────┬───────┐ │ 고객번호 │ 이름 │ │ 주문번호 │ 고객번호 │ 날짜 │ ├──────────┼──────┤ ├──────────┼──────────┼───────┤ │ 1 │김철수│ ◀── │ 101 │ 1 │10-05 │ │ 2 │이영희│ │ 102 │ 2 │10-06 │ └──────────┴──────┘ └──────────┴──────────┴───────┘ 기본키 외래키 → 고객의 기본키를 참조
외래키에는 NULL이 허용됩니다 "어느 부서에도 속하지 않은 사원"처럼 참조가 없는 상태가 현실에 존재하기 때문입니다. 참조 무결성 위반은 NULL이 아니라 존재하지 않는 값을 가리킬 때입니다.
5관계 데이터 모델의 제약조건 — 두 가지 무결성
개체 무결성의 제약조건

기본키를 구성하는 모든 속성은 NULL값을 가지면 안 된다.

INSERT INTO 고객 (고객번호, 이름) VALUES (NULL, '김철수'); ✗ 위반

이유: 기본키는 튜플을 식별하는 유일한 수단입니다. NULL이면 식별할 수 없습니다.

참조 무결성의 제약조건

외래키는 참조할 수 없는 값을 가질 수 없다.

INSERT INTO 주문 (주문번호, 고객번호) VALUES (103, 999); ✗ 위반 (고객 999 없음)

이유: 존재하지 않는 고객을 가리키는 주문은 의미가 없습니다. 단, NULL은 허용됩니다.

# 역할
너는 관계 데이터 모델과 키 설계를 가르치는 튜터이자 스키마 리뷰어다.

# 배경
나는 아래 릴레이션의 키를 정하고 무결성 제약을 설계하려고 한다.
- 릴레이션: [이름]
- 속성과 값 예시:
  [예]
  고객번호: 1, 2, 3        (자동 증가)
  이름    : 김철수, 이영희   (중복 가능)
  이메일  : a@shop.com …    (현재 중복 없음, 변경 가능)
  연락처  : 010-1111-1111, NULL  (없는 사람 있음)
  등급    : VIP, 일반, 휴면
- 업무 규칙: [예: 한 이메일로 두 계정을 만들 수 없다 / 고객은 등급이 반드시 있어야 한다]
- 쓰는 DBMS: [MySQL / PostgreSQL]

# 하고 싶은 일 (해당하는 번호만 남긴다)
A. 키 후보 찾기: 슈퍼키 → 후보키 → 기본키 → 대체키를 순서대로 도출하고, 각 후보가 유일성·최소성을 만족하는지 판정한다.
B. 기본키 선정: 세 가지 기준(NULL 가능성, 변경 빈도, 단순성)으로 점수를 매겨 기본키를 추천한다.
C. 대리키 검토: 자연키가 부적합할 때 대리키(자동 증가/IDENTITY/UUID)를 쓸지 판단하고 이유를 적는다.
D. 무결성 제약: 개체 무결성과 참조 무결성을 실제 DDL로 표현한다.
E. 위반 실험: 각 제약을 일부러 위반하는 INSERT/UPDATE 문과 예상 오류 메시지를 만든다.
F. 확인 질문: 키와 무결성에 대한 3지선다 문제 5개를 해설과 함께 만든다.

# 반드시 지킬 것
1. 후보키 판정에서 "유일성"과 "최소성"을 각각 따로 판정하고 근거를 적는다.
2. NULL이 가능한 속성은 기본키 후보에서 반드시 제외한다. 이유도 적는다.
3. 값이 변경될 수 있는 속성(이메일·전화번호 등)은 기본키로 권하지 않는다.
4. 외래키에는 NULL이 허용된다는 점을 명시한다. 참조 무결성 위반은 '존재하지 않는 값'일 때만이다.
5. ON DELETE / ON UPDATE 정책을 반드시 명시하고, 그 선택이 업무 규칙과 어떻게 맞는지 적는다.
6. 지어내지 않는다. 내가 준 속성 외에 추가하지 않는다.
7. 주석과 설명은 한국어로, 입문자도 따라올 수 있게 쓴다.

"변경 가능한 속성은 기본키로 권하지 않는다"이메일을 기본키로 쓰면 회사가 바뀔 때마다 참조가 흔들립니다.
"위반 실험 SQL"제약을 실제로 깨 보는 것이 가장 확실한 검증입니다.
G5흔한 오류와 해결
증상원인해결
이메일을 기본키로 추천변경 가능성을 고려하지 않음변경 빈도를 함께 판단하게 요청합니다.
복합키를 무조건 기본키로단순성 기준 누락세 가지 기준으로 점수를 매기게 합니다.
외래키에 NOT NULL을 붙임NULL 허용 규칙 오해"외래키에는 NULL이 허용된다"를 강조합니다.
삭제 정책이 빠짐DDL만 요청ON DELETE/UPDATE 정책을 함께 요구합니다.
G6체크리스트
  • 모든 후보키에 유일성·최소성 판정이 있는가
  • NULL 가능 속성이 기본키에서 제외됐는가
  • 변경 가능성이 검토됐는가
  • 삭제·수정 정책이 업무 규칙과 맞는가
  • 위반 실험을 실제로 실행했는가
G7미니 과제
과제주문상세(주문번호, 상품번호)를 복합 기본키로 쓸지, 대리키를 추가할지 위 프롬프트로 리뷰받아 보세요. 두 설계의 장단점을 표로 정리하면 실무 감각이 붙습니다.

  email       VARCHAR(120) NOT NULL,
  phone       VARCHAR(20) NULL,                  -- NULL 허용

  order_id    INT NOT NULL AUTO_INCREMENT,

G4라인별 해설
줄설명
PRIMARY KEY (customer_id)개체 무결성의 구현입니다. MySQL에서는 기본키 열에 자동으로 NOT NULL이 붙습니다.
UNIQUE KEY대체키를 살려 두는 방법입니다. 후보키였지만 기본키로 선택되지 않은 키입니다.
phone VARCHAR(20) NULLNULL 허용 — 기본키 후보에서 탈락시키는 이유입니다.
ON DELETE RESTRICT주문이 있는 고객은 삭제 불가. 이력 보존이 중요한 업무에 맞습니다.
ON UPDATE CASCADE고객번호가 바뀌면 주문의 외래키도 따라 바뀝니다.
실험 ①의 주의AUTO_INCREMENT 열에 NULL을 넣으면 값을 채워 넣어 성공합니다. 개체 무결성 위반을 보려면 컬럼에서 AUTO_INCREMENT를 뺀 상태로 실험해야 합니다.
실험 ④CHECK는 MySQL 8.0.16부터 실제로 동작합니다. 그 이전 버전에서는 문법만 허용되고 무시됩니다.

G2실행 순서

  2. 점검기본키·대체키·외래키 위반을 각각 셉니다.
  3. 정리위반 행을 분리합니다.
  4. 적재정상 행만 넣고 위반 행은 리포트합니다.
G3전체 코드
# -*- coding: utf-8 -*-
"""6주차 실습 — 적재 전 키·무결성 위반 점검"""
import pandas as pd
from sqlalchemy import create_engine

customers = pd.DataFrame({
    "customer_id": [1, 2, 3, 3],                 # 3 중복 → 기본키 위반
    "name":        ["김철수","이영희","박민수","박민수2"],
    "email":       ["a@shop.com","b@shop.com","c@shop.com","a@shop.com"],  # 중복 → 대체키 위반
    "grade":       ["VIP","일반","VVIP","일반"],   # VVIP → 도메인 위반
})
orders = pd.DataFrame({
    "order_id":    [101, 102, 103],
    "customer_id": [1, 2, 99],                    # 99 없음 → 참조 무결성 위반
})

print("=== ① 개체 무결성(기본키) 점검 ===")
pk_dup = customers[customers.duplicated("customer_id", keep=False)]
print(pk_dup if len(pk_dup) else "위반 없음")
pk_null = customers[customers["customer_id"].isna()]
print("기본키 NULL:", len(pk_null))

print("\n=== ② 대체키(UNIQUE) 점검 ===")
uq_dup = customers[customers.duplicated("email", keep=False)]
print(uq_dup[["customer_id","name","email"]] if len(uq_dup) else "위반 없음")

print("\n=== ③ 도메인(CHECK) 점검 ===")
allowed = {"VIP", "일반", "휴면"}
bad = customers[~customers["grade"].isin(allowed)]
print(bad[["customer_id","grade"]] if len(bad) else "위반 없음")

print("\n=== ④ 참조 무결성(FK) 점검 ===")
orphan = orders[~orders["customer_id"].isin(customers["customer_id"])]
print(orphan if len(orphan) else "위반 없음")

# ── 정리: 정상 행만 적재하고 위반 행은 따로 리포트 ──
def clean(customers, orders):
    c = (customers
         .dropna(subset=["customer_id"])
         .drop_duplicates("customer_id", keep="first")     # 기본키 중복 제거
         .pipe(lambda d: d[~d.duplicated("email", keep="first")])   # 대체키 중복 제거
         .pipe(lambda d: d[d["grade"].isin({"VIP","일반","휴면"})]))
    o = orders[orders["customer_id"].isin(c["customer_id"])]
    return c, o, len(customers) - len(c), len(orders) - len(o)

c_ok, o_ok, dropped_c, dropped_o = clean(customers, orders)
print(f"\n정상 고객 {len(c_ok)}건 / 제외 {dropped_c}건")
print(f"정상 주문 {len(o_ok)}건 / 제외 {dropped_o}건")

# ── 실제 적재 (제약이 살아 있는 DB라면 위반 행이 자동으로 막힌다) ──
# engine = create_engine("mysql+mysqlconnector://...")

G4라인별 해설
줄설명
duplicated(keep=False)중복된 모든 행을 표시합니다. keep="first"는 첫 행만 남깁니다.
isin(allowed)SQL의 CHECK (grade IN …)을 미리 흉내 냅니다.
~isin(customer_id)부모에 없는 자식 행(고아 레코드)을 찾습니다. 참조 무결성 위반입니다.
정리 순서부모를 먼저 정리한 뒤 자식을 정리해야 합니다. 순서를 바꾸면 정상 행까지 버립니다.
리포트몇 건이 제외됐는지 반드시 숫자로 남깁니다. 조용히 사라지는 것이 가장 위험합니다.

IntegrityError: Cannot add or update a child row부모 적재 전에 자식 적재부모 → 자식 순서를 지킵니다.
제외 건수가 0인데 오류 발생점검 기준과 DB 제약이 다름데이터 사전에서 실제 제약을 읽어 기준을 맞춥니다.
NaN이 기본키로 들어감결측치 처리 누락dropna(subset=[pk])를 먼저 실행합니다.

  • 제외 건수를 숫자로 남겼는가

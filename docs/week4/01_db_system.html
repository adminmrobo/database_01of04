2스키마(Schema)란

데이터베이스의 구조와 제약 조건에 관한 명세입니다. 데이터가 아니라 데이터의 틀입니다. 그리고 이 틀은 한 겹이 아니라 세 겹으로 나뉘어 있습니다.

하나의 DB, 세 가지 스키마 하나의 DB에는 3가지 유형의 스키마가 존재하지만, 이는 DB를 바라보는 관점이 다를 뿐 모두 같은 DB를 표현합니다. · 실제 데이터는 물리적 저장장치에 저장된 DB · DB 접근을 위해서는 내부 스키마에 따라 지정된 DB에만 접근해야 함
3데이터 사전 — 데이터를 위한 데이터

DB에 저장돼 있는 데이터를 정확하고 효율적으로 이용하기 위한 스키마, 사상 정보 등을 저장하고 있습니다. 곧 메타데이터입니다.

3단계 데이터베이스 구조Three-Level Architecture

ANSI/SPARC 3단계 구조. 외부·개념·내부 세 층으로 나누고 그 사이를 사상(Mapping)으로 잇습니다.

1외부 스키마

사용자나 응용 프로그램이 필요한 데이터베이스의 논리적 구조를 정의합니다. 3단계 중 최상위 단계입니다.

별칭사용자 뷰(View)의 집합
보안사용자별로 접근할 데이터를 제한
독립성개념 스키마가 바뀌어도 이를 흡수
온라인 쇼핑몰 고객 — 상품정보, 가격, 리뷰 / 판매자 — 상품정보, 재고량, 판매통계 / 관리자 — 모든 정보
2개념 스키마

조직 전체의 관점에서 데이터베이스를 정의한 논리적 구조입니다. 중간 계층이며 DBA의 관리 대상입니다.

범위조직 전체의 통합된 데이터 뷰, 전사적 데이터 정의
내용엔티티·속성·관계 정의 + 무결성 제약조건
관리보안 및 무결성 정책 구현

예: 대학 DB의 개념 스키마 — 학생·교수·과목·수강 엔티티와 그들 간의 관계(수강신청, 과목 담당, 학점 부여).

3내부 스키마

데이터베이스의 물리적 저장 구조를 정의하는 가장 낮은 레벨입니다. 데이터가 실제로 저장 장치에 어떻게 저장되는지의 명세입니다.

파일 구조블록 크기, 페이지 구조, 레코드 포맷
인덱스B-트리, 해시, 인덱스 조직화
접근 경로순차 접근, 인덱스 접근, 포인터
저장 영역디스크 할당, 버퍼 관리

03

데이터 독립성 — 이름을 바꾸면 무슨 일이?Data Independence

도입 질문에 답할 차례입니다. 개념 스키마에서 '연락처'를 '전화번호'로 바꾸면, 응용 프로그램과 테이블은 어떻게 될까요?

1단계 애니메이션 — 이름 변경이 파급되는 범위
외부 스키마 : 고객 앱 → [ 연락처, 이름 ] ↓ 외부/개념 사상 개념 스키마 : customer( 연락처 , name ) ↓ 개념/내부 사상 내부 스키마 : CUSTOMER_T.dat / IDX_CUSTOMER

처음 상태입니다. 개념 스키마에 연락처라는 이름이 있습니다.

외부 스키마 : 고객 앱 → [ 연락처, 이름 ] ← 그대로 유지 ↓ 외부/개념 사상 ← 여기만 수정 개념 스키마 : customer( 전화번호 , name ) ← 이름 변경 ↓ 개념/내부 사상 내부 스키마 : CUSTOMER_T.dat / IDX_CUSTOMER

개념 스키마의 이름이 바뀌었습니다. 외부/개념 사상만 수정하면 됩니다.

외부 스키마 : 고객 앱 → [ 연락처, 이름 ] ← 바뀌지 않음 ↓ 외부/개념 사상 (연락처 ← 전화번호 로 연결) 개념 스키마 : customer( 전화번호 , name ) ↓ 개념/내부 사상 내부 스키마 : CUSTOMER_T.dat / IDX_CUSTOMER

응용 프로그램은 한 줄도 고치지 않습니다. 사상이 이름 차이를 흡수했기 때문입니다.

외부 스키마 : 고객 앱 → [ 연락처, 이름 ] ↓ 외부/개념 사상 개념 스키마 : customer( 전화번호 , name ) ↓ 개념/내부 사상 ← 여기만 수정 내부 스키마 : CUSTOMER_T.dat → 저장 매체·인덱스 교체

이번엔 내부 스키마를 바꿉니다(인덱스 추가, 저장 매체 교체). 개념 스키마는 그대로입니다.

결론 · 개념 스키마 변경 → 외부 스키마 영향 X : 논리적 데이터 독립성 · 내부 스키마 변경 → 개념 스키마 영향 X : 물리적 데이터 독립성 · 테이블을 고치는 것이 아니라, 사상 정보를 고친다

이름 변경은 테이블 수정이 아니라 사상 수정입니다. 그래서 응용 프로그램이 살아남습니다.

  • ② 개념 스키마에서 전화번호로 변경
  • ③ 외부/개념 사상만 수정 → 응용 프로그램 무사
  • ④ 내부 스키마 변경(인덱스·매체)
  • ⑤ 두 독립성의 정리
2데이터 독립성

개념 스키마가 변경되더라도 외부 스키마에 영향이 없고, 전체 데이터베이스의 논리적 구조가 변경되어도 외부 스키마는 바뀌지 않습니다. 논리적 구조가 변경되더라도 관련된 외부/개념 사상 정보를 적절히 수정하면 됩니다.

예시 개념 스키마에서 데이터 이름이 "연락처"가 "전화번호"로 변경 → 외부/개념 사상만 수정합니다. 테이블을 수정하지 않습니다.
3사상(Mapping)

각 스키마 사이의 대응관계를 사상 또는 매핑(Mapping)이라고 합니다. 응용 인터페이스 역할을 합니다.

사상잇는 것담당 독립성
외부/개념 사상사용자 뷰 ↔ 통합 논리 구조논리적 데이터 독립성
개념/내부 사상통합 논리 구조 ↔ 물리 저장 구조물리적 데이터 독립성
내부 스키마 변경 사례 인덱스 추가, 클러스터링 변경, 저장 매체 교체 등 물리적 저장 방식 변경 시에도 응용 프로그램 수정 없이 실행 가능합니다.

3절차적 조작어 vs 비절차적 조작어
절차적 조작어 (Procedural)
  • "어떻게"까지 지정 — 어떤 순서로, 어떤 인덱스를 쓸지
  • 성능을 직접 통제할 수 있지만 코드가 길어짐
비절차적 조작어 (Non-procedural)
  • "무엇을"만 지정 — SQL이 여기 해당
  • 짧고 이식성이 좋으며, 최적화는 DBMS가 담당
SQL은 왜 비절차적인가 같은 SELECT도 인덱스가 있으면 인덱스로, 없으면 전체 스캔으로 실행됩니다. 실행 방법을 질의처리기와 옵티마이저가 정하기 때문입니다.

목표: 뷰(View)로 외부 스키마를 만들고, 데이터 사전을 직접 조회해 보기.

G1언제 쓰나

여러 사용자(고객·판매자·관리자)에게 다른 뷰를 제공해야 할 때, 각 뷰에 무엇을 넣고 무엇을 감출지 설계할 때 씁니다.

G2실행 순서
  1. 사용자 목록시스템을 쓰는 사람 그룹을 적습니다.
  2. 프롬프트 채우기각 그룹이 무엇을 봐야 하고 무엇을 보면 안 되는지 적습니다.
  3. 설계 받기뷰 정의와 권한 부여 문장을 받습니다.
  4. 검증숨겨야 할 열이 정말 빠졌는지 확인합니다.
G3프롬프트 전체
# 역할
너는 데이터베이스 3단계 구조(외부·개념·내부 스키마)를 가르치는 설계 튜터다.

# 배경
나는 아래 사용자 그룹에게 서로 다른 데이터를 보여 주는 시스템을 설계하려고 한다.
- 개념 스키마(전체 테이블): [테이블 이름과 열 목록]
- 사용자 그룹: [예: 고객, 판매자, 관리자, 배송기사]
- 각 그룹이 봐야 할 것 / 보면 안 되는 것: [예: 고객은 자기 주문만, 판매자는 자기 상품의 판매통계만, 관리자는 전부]
- 쓰는 DBMS: [MySQL / PostgreSQL]

# 하고 싶은 일 (해당하는 번호만 남긴다)
A. 외부 스키마 설계: 각 사용자 그룹별 뷰(VIEW) 정의문을 만든다.
B. 권한 설계: 각 뷰에 대한 GRANT 문과, 원본 테이블 접근을 막는 방법을 만든다.
C. 사상 설명: 외부/개념 사상이 각 뷰에서 어떻게 동작하는지 표로 정리한다.
D. 변경 시나리오: 개념 스키마에서 열 이름을 바꿨을 때, 각 뷰와 응용 프로그램에 생기는 영향과 대응 절차를 단계로 적는다.
E. 확인 질문: 3단계 구조와 데이터 독립성에 대한 3지선다 문제 5개를 해설과 함께 만든다.

# 반드시 지킬 것
1. 뷰 정의에는 반드시 원본 테이블의 기본키를 포함한다. (뷰를 갱신 가능하게 유지하기 위해)
2. 숨겨야 할 열을 SELECT * 로 노출하지 않는다. 열을 하나씩 나열한다.
3. 권한은 뷰에만 주고 원본 테이블 권한은 회수한다.
4. "개념 스키마를 바꾸면 테이블을 수정한다"는 표현을 쓰지 않는다. 사상 수정이라는 점을 명확히 적는다.
5. 지어내지 않는다. 내가 준 테이블·열 목록에 없는 것을 추가하지 않는다.
6. 주석과 설명은 한국어로, 입문자도 따라올 수 있게 쓴다.

# 답변 형식
1. 한 줄 요약 (사용자 그룹 수, 가장 민감한 열)
2. 그룹별 뷰 정의 SQL과 GRANT 문
3. 외부/개념 사상 표 (뷰 열 ↔ 개념 스키마 열)
4. 열 이름 변경 시나리오의 단계별 대응 절차
5. 다음에 해 볼 일 2~3가지

# 스키마
[여기에 테이블과 열 목록, 사용자 그룹의 권한 요구를 붙여 넣는다]
G4라인별 해설
문장의도
"뷰에 기본키를 포함한다"기본키가 빠진 뷰는 갱신이 불가능해집니다. 실무에서 자주 놓치는 함정입니다.
"SELECT * 금지"주민번호·연락처 같은 민감 열이 의도치 않게 노출되는 것을 막습니다.
"원본 테이블 권한 회수"뷰로 막아도 원본에 권한이 있으면 우회할 수 있습니다.
"사상 수정이라는 점을 명확히"이 편의 핵심 개념을 AI 답변에서도 어긋나지 않게 고정합니다.
G5흔한 오류와 해결
증상원인해결
뷰가 갱신 불가로 나옴기본키·조인·집계 포함기본키를 포함하고 집계는 별도 요약 뷰로 분리합니다.
숨긴 열이 그대로 보임SELECT * 사용열을 명시적으로 나열하게 다시 요청합니다.
권한 오류가 계속 발생뷰 권한과 원본 권한이 충돌GRANT … ON 뷰만 주고 원본은 REVOKE 합니다.
G6체크리스트
  • 모든 뷰에 기본키가 포함됐는가
  • 민감 열이 노출되지 않는가
  • 원본 테이블 권한을 회수했는가
  • 각 그룹이 자기 데이터만 보는지 실제 계정으로 확인했는가
G7미니 과제
과제고객 뷰에서 email을 contact으로 이름을 바꿔 보세요. 그러면 뷰 정의만 고치면 되는지, 테이블도 고쳐야 하는지 판단하고 근거를 한 줄로 적어 보세요.
G1언제 쓰나

G2실행 순서

  2. 뷰 만들기역할별 뷰 2개를 만듭니다.
  3. 권한 주기계정을 만들고 뷰에만 권한을 줍니다.
  4. 데이터 사전 조회구조가 어디에 기록됐는지 확인합니다.

G2실행 순서

  2. 뷰역할별 뷰를 만듭니다.
  3. 권한뷰에만 SELECT를 줍니다.
  4. 카탈로그 조회데이터 사전을 직접 봅니다.
G3전체 코드
CREATE SCHEMA IF NOT EXISTS shop;
SET search_path TO shop, public;

CREATE TABLE IF NOT EXISTS customer (
  customer_id integer GENERATED ALWAYS AS IDENTITY,
  name  varchar(30)  NOT NULL,
  email varchar(120) NOT NULL UNIQUE,
  phone varchar(20),
  addr  varchar(200),
  CONSTRAINT pk_customer PRIMARY KEY (customer_id)
);

-- [1] 역할(ROLE) — PostgreSQL은 사용자와 그룹을 같은 개념으로 다룬다
DO $$ BEGIN
  IF NOT EXISTS (SELECT 1 FROM pg_roles WHERE rolname='app_customer') THEN
    CREATE ROLE app_customer LOGIN PASSWORD 'ChangeMe!234';
  END IF;
END $$;

-- [2] 외부 스키마(뷰)
CREATE OR REPLACE VIEW v_customer_self AS
SELECT customer_id, name, addr
FROM customer;

-- [3] 권한 — 뷰에만 준다. 스키마 사용 권한도 필요하다.
GRANT USAGE  ON SCHEMA shop TO app_customer;
GRANT SELECT ON shop.v_customer_self TO app_customer;
REVOKE ALL ON shop.customer FROM app_customer;   -- 원본은 명시적으로 회수

-- [4] 데이터 사전(pg_catalog) 직접 조회
SELECT c.relname AS 객체, c.relkind AS 종류
FROM pg_class c JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE n.nspname = 'shop';        -- relkind: r=테이블, v=뷰

SELECT column_name, data_type, is_nullable
FROM information_schema.columns
WHERE table_schema='shop' AND table_name='v_customer_self';

-- [5] 뷰 정의(사상) 확인
SELECT definition FROM pg_views
WHERE schemaname='shop' AND viewname='v_customer_self';

-- [6] [차이] 열 단위 권한 — PostgreSQL만 가능
--     customer 테이블의 name, addr 열만 열어 주고 email, phone은 감춘다
GRANT SELECT (customer_id, name, addr) ON shop.customer TO app_customer;

G2실행 순서

  2. 카탈로그 조회테이블·열·타입을 읽습니다.
  3. 문서화마크다운 표로 저장합니다.
  4. 비교이전 스키마와 달라진 점을 찾습니다.
G3전체 코드
# -*- coding: utf-8 -*-
"""4주차 실습 — 데이터 사전을 읽어 스키마 문서 만들기"""
import os
import pandas as pd
from sqlalchemy import create_engine

# [1] 접속 정보는 코드에 쓰지 않는다 (환경변수에서 읽는다)
URL = os.environ.get(
    "SHOP_DB_URL",
    "mysql+mysqlconnector://root:비밀번호@127.0.0.1:3306/shop?charset=utf8mb4",
)
engine = create_engine(URL)

# [2] 데이터 사전 조회 — information_schema 가 곧 메타데이터
cols = pd.read_sql("""
    SELECT TABLE_NAME  AS 테이블,
           COLUMN_NAME AS 열,
           DATA_TYPE   AS 타입,
           IS_NULLABLE AS NULL허용,
           COLUMN_KEY  AS 키종류
    FROM information_schema.COLUMNS
    WHERE TABLE_SCHEMA = 'shop'
    ORDER BY TABLE_NAME, ORDINAL_POSITION
""", engine)
print(cols)

# [3] 테이블과 뷰 구분
objs = pd.read_sql("""
    SELECT TABLE_NAME AS 객체, TABLE_TYPE AS 종류
    FROM information_schema.TABLES
    WHERE TABLE_SCHEMA = 'shop'
""", engine)
print(objs)

# [4] 외부 스키마(뷰)의 정의 = 사상 정보
views = pd.read_sql("""
    SELECT TABLE_NAME AS 뷰, VIEW_DEFINITION AS 정의
    FROM information_schema.VIEWS
    WHERE TABLE_SCHEMA = 'shop'
""", engine)
print(views)

# [5] 문서로 내보내기
with open("schema_doc.md", "w", encoding="utf-8") as f:
    f.write("# shop 스키마 문서 (데이터 사전에서 자동 생성)\n\n")
    for t, g in cols.groupby("테이블"):
        kind = objs.loc[objs["객체"] == t, "종류"].iloc[0]
        f.write(f"## {t}  ({kind})\n\n")
        f.write(g[["열", "타입", "NULL허용", "키종류"]].to_markdown(index=False))
        f.write("\n\n")
print("schema_doc.md 생성 완료")

# [6] 이전 스키마와 비교 — 변경 감지
def snapshot(engine, path="schema_snapshot.csv"):
    df = pd.read_sql("""
        SELECT TABLE_NAME, COLUMN_NAME, DATA_TYPE, IS_NULLABLE
        FROM information_schema.COLUMNS WHERE TABLE_SCHEMA='shop'
    """, engine)
    if os.path.exists(path):
        old = pd.read_csv(path)
        merged = old.merge(df, how="outer", indicator=True)
        changed = merged[merged["_merge"] != "both"]
        print("스키마 변경점:\n", changed if len(changed) else "변경 없음")
    df.to_csv(path, index=False)

snapshot(engine)

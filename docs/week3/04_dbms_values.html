04

DBMS가 제공하는 핵심 가치Core Values

보충 자료에서 정리한 여섯 가지입니다. 각 항목은 앞으로 배울 챕터와 하나씩 연결됩니다.

1데이터 통합

여러 응용 프로그램이 통합 데이터베이스를 공유해 일관성을 확보합니다.

이어지는 곳3단계 구조(4편) — 통합된 뷰를 어떻게 나눠 보여 줄지
2중복 최소화

데이터 중앙 관리로 저장공간을 절약하고 불일치를 방지합니다.

이어지는 곳정규화(8장) — 중복을 어디까지 줄일지의 규칙
3데이터 독립성

물리적·논리적 독립성으로 구조 변경 시 응용 프로그램에 영향이 없습니다.

이어지는 곳사상(Mapping)과 스키마(4편)
4트랜잭션 관리

ACID 특성을 보장하고 안전한 데이터 처리와 장애 복구 기능을 제공합니다.

이어지는 곳트랜잭션과 회복(12~13장)
5동시성 제어

다수 사용자의 동시 접근을 조정해 데이터 일관성을 유지합니다.

이어지는 곳잠금과 격리 수준(12장)
6데이터 보안

세분화된 권한 관리로 사용자별로 볼 수 있는 범위를 나눕니다.

이어지는 곳외부 스키마(4편)와 DCL
7ACID를 한 줄씩
특성뜻없으면 벌어지는 일
원자성 (Atomicity)전부 되거나, 전부 안 되거나계좌 이체에서 한쪽만 반영됨
일관성 (Consistency)규칙을 깨는 값이 저장되지 않음재고가 음수가 됨
고립성 (Isolation)동시 작업이 서로를 방해하지 않음같은 좌석을 두 명에게 판매
지속성 (Durability)커밋된 값은 사라지지 않음정전 후 결제 기록 소실
조수실습·질문

DBMS를 쓰면 무조건 좋은 걸까요?

박사설계 원리

아닙니다. 중복 통제를 얻는 대신 비용과 복잡성을 냅니다.

M-RoboDB 안내

삐빅 — 휴먼, 중앙관리에는 취약점도 따릅니다.

초파리 연구원코드·데이터

공짜는 없다. 대신 무엇을 얻는지 정확히 알면 된다.

06

실무 사례 — 세 기업은 어떻게 풀었나Real-World Cases

같은 중복 문제를 세 회사가 서로 다르게 해결했습니다. 무엇이 달랐는지 보면 "DBMS를 도입한다"가 하나의 답이 아니라는 것을 알 수 있습니다.

1쿠팡 — MSA와 CMDB

수백 개 마이크로서비스가 각자 DB를 두면서 고객 주소·상품 정보가 서비스마다 중복 저장되고 불일치가 생겼습니다. 프론트엔드에도 호출 로직이 중복됐습니다.

해결 1자체 CMDB(Configuration Management DB) 구축
해결 2코어 서빙(Core Serving) 계층으로 통합 데이터 제공
해결 3메타 DB로 서비스·자원 통합 관리

코어 서빙 계층의 특징: 각 마이크로서비스 데이터를 단일 API로 통합 제공, 실시간/일반 캐시 이중 구조, 통합 NoSQL DB로 중복 최소화. 캐시 무효화 기술로 실시간 갱신을 처리합니다.

2페이스북/메타 — 캐시와 그래프 DB

초당 수백만 건의 요청, 급증하는 읽기 부하, 지연 시간 최소화가 과제였습니다.

캐시수천 대 서버에 Memcache 클러스터링, Look-aside 패턴
일관성리전 간 데이터 일관성 유지 프로토콜
그래프TAO — 사용자·게시물은 노드, 관계는 엣지

효과: DB 부하 95% 이상 감소, 밀리초 단위 응답. 소셜 그래프는 샤딩으로 수천 대 서버에 분산 저장했습니다.

3트위터(X) — 폴리글랏 퍼시스턴스

초당 수천 건의 트윗, 수억 명 사용자. RDBMS만으로는 실시간 처리와 확장에 한계가 있었습니다.

MongoDB사용자 프로필·트윗 등 비정형 데이터
Redis인메모리 캐싱 — 타임라인, 트렌딩 토픽
MySQL트랜잭션이 필요한 결제·핵심 사용자 데이터

데이터 특성에 맞게 여러 DB를 혼합 사용하는 전략을 폴리글랏 퍼시스턴스라고 합니다. 초당 5,700개 이상 트윗, 일일 2억 개 이상 활성 트윗을 처리합니다.

4세 사례에서 뽑아낸 세 문장
1 중복은 저장을 줄여서가 아니라 기준을 하나 정해서 해결합니다 — 쿠팡의 메타 DB, 코어 서빙 계층.
2 읽기 부하는 캐시로, 관계 탐색은 그래프로 — 저장소를 역할별로 나눕니다.
3 하나의 DBMS로 모두를 해결하려 하지 않습니다 — 트위터의 폴리글랏 퍼시스턴스.

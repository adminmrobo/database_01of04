DBMS 세대별 발전사Generations

데이터 처리 요구가 바뀔 때마다 DBMS의 모양도 바뀌었습니다. 네 세대를 따라가면 지금 왜 관계형과 NoSQL을 함께 쓰는지가 이해됩니다.

3세대1980~90년대객체지향 · 객체관계형복잡한 타입, 상속·다형성표준과 도구의 파편화ObjectStore, Versant, ObjectDB / PostgreSQL, Oracle(객체 확장)

21세대 — 계층형과 네트워크형

계층형은 부모-자식 관계의 트리 구조입니다. 구조가 단순하고 접근이 빠르지만 다대다 관계를 표현할 수 없고 구조를 바꾸기 어렵습니다. IBM의 IMS가 대표적입니다.

네트워크형은 레코드 간 다양한 관계를 표현할 수 있는 그래프 구조입니다. 다대다가 가능하고 복잡한 구조를 지원하지만, 구조 자체가 복잡하고 물리적 구조에 종속됩니다. IDMS, CODASYL이 대표적입니다.

32세대 — 관계형 DBMS

1970년대 E.F. Codd의 논문 "A Relational Model of Data for Large Shared Data Banks"에서 처음 제안된 관계형 모델 기반 DBMS입니다. 데이터를 테이블(릴레이션) 형태로 저장하고 관리합니다.

표현행(튜플)과 열(속성)로 구성된 2차원 테이블
관계기본키와 외래키를 통한 테이블 간 관계 설정
질의SQL을 통한 직관적인 데이터 조작
보장ACID 트랜잭션 보장
customer 테이블 (관계 DBMS의 사례) ┌─────────────┬────────┬──────────────────┐ │ customer_id │ name │ email │ ← 속성(열) ├─────────────┼────────┼──────────────────┤ │ 1 │ 김철수 │ chulsoo@shop.com │ ← 튜플(행) │ 2 │ 이영희 │ younghee@shop.com│ └─────────────┴────────┴──────────────────┘

이 강의에서 설계할 대상이 바로 이 관계형 모델입니다. 4~6편에서 이 표를 만드는 규칙을 배웁니다.

43세대 — 객체지향 · 객체관계형
객체지향 DBMS (OODBMS)
  • 객체를 그대로 저장
  • 복잡한 데이터 타입과 관계 표현이 용이
  • ObjectStore, Versant, ObjectDB
객체관계형 DBMS (ORDBMS)
  • 관계형 DB에 객체지향 개념을 통합
  • 사용자 정의 타입 지원
  • Oracle(객체 확장), PostgreSQL, IBM DB2

주요 장점은 복잡한 데이터 모델링 가능성, 상속 및 다형성 지원, 재사용성 향상입니다. CAD/CAM, GIS, 멀티미디어 데이터베이스, 과학 응용 분야에서 쓰입니다.

54세대 — NoSQL과 NewSQL

NoSQL(Not Only SQL)은 관계형 DB의 한계를 극복하려 2000년대 후반 등장했습니다. 빅데이터 대응, 수평적 확장성, 웹스케일 지원, 유연한(스키마리스) 스키마가 특징입니다.

유형구조예
문서형JSON/BSON 문서 저장MongoDB, CouchDB
키-값단순 키-값 쌍Redis, DynamoDB
컬럼형연관 데이터 컬럼 저장Cassandra, HBase
그래프형노드와 관계Neo4j, JanusGraph

NewSQL은 NoSQL과 SQL의 장점을 결합합니다. 관계형 모델과 확장성을 통합하고 ACID 트랜잭션을 지키며 분산 아키텍처를 씁니다 — Google Spanner, CockroachDB, VoltDB.

SQL (2세대)NoSQL (4세대)NewSQL
데이터정형비정형하이브리드
일관성강한 일관성최종 일관성ACID 트랜잭션
확장수직적 확장수평적 확장분산 아키텍처
64세대 이후의 질문 — 빅데이터 3V와 일관성

비정형 데이터와 빅데이터(3V: Volume·Variety·Velocity)에서는 안정성과 일관성을 유지할 수 있는가가 계속 문제로 남습니다. 그래서 해시태그처럼 관계 자체가 데이터인 경우(태그 사이의 연결)에는 그래프 DB가, 단순 조회가 폭주하는 경우에는 인메모리 캐시가 함께 쓰입니다.

정답은 하나가 아닙니다 페이스북·인스타그램의 검색과 해시태그, 대규모 트래픽 처리를 보면 하나의 DBMS로 모든 것을 해결하려는 접근이 실패한다는 것을 알 수 있습니다. 역할별로 다른 저장소를 조합하는 것이 현대적 설계입니다.

G3프롬프트 전체
# 역할
너는 데이터베이스 관리 시스템(DBMS) 도입을 검토하는 컨설턴트이자 설계 튜터다.

# 배경
나는 파일(또는 스프레드시트) 기반으로 데이터를 관리하고 있고, DBMS 도입을 검토 중이다.
- 지금 관리하는 파일: [파일/시트 이름과 각각 담긴 내용]
  예: 고객정보.dat(고객 주소·연락처), 주문.xls(주문 내역·배송지), 재고.xls(상품·수량)
- 사람 수 / 부서 수: [ ], 하루 갱신 건수: [ ]
- 같은 값이 여러 곳에 저장되는 항목: [예: 고객 주소, 상품 단가]
- 겪고 있는 사고: [예: 주소 변경 누락으로 오배송, 재고 불일치]
- 도입 후보 DBMS: [MySQL / PostgreSQL / 아직 모름]

# 하고 싶은 일 (해당하는 번호만 남긴다)
A. 문제 진단: 아래 다섯 문제(데이터 중복, 데이터 종속성, 동시 공유·보안·회복 부족, 응용 프로그램 개발의 어려움, 무결성 유지의 어려움) 중 내 상황이 어디에 해당하는지 근거와 함께 진단한다.
B. 개선안: 각 문제에 대해 DBMS의 어떤 기능이 대응되는지 표로 정리한다.
C. 도입 순서: 무엇부터 손대야 하는지 4~6단계 로드맵을 제안한다.
D. 위험 요소: 도입 시 생길 단점(비용, 백업·회복의 복잡성, 중앙관리 취약점, 인력)을 내 상황에 맞게 짚는다.
E. 검증 질문: 이 내용을 확인하는 3지선다 문제 5개를 해설과 함께 만든다.

# 반드시 지킬 것
1. "중복을 없앤다"가 아니라 "중복을 통제한다"는 표현을 쓴다. 이유도 함께 적는다.
2. 데이터 종속성은 반드시 "파일 구조가 바뀌면 프로그램을 고쳐야 하는가"라는 질문으로 진단한다.
3. 회복(롤백)이 안 되는 상황에서 실제로 어떤 값이 어긋나는지 구체적 예시를 하나 든다.
4. 도입 효과를 수치로 말할 때는 근거를 밝히고, 근거가 없으면 수치를 만들지 않는다.
5. 단점을 반드시 함께 적는다. 장점만 나열하지 않는다.
6. 주석과 설명은 한국어로, 입문자도 따라올 수 있게 쓴다.

# 답변 형식
1. 한 줄 진단 (가장 심각한 문제 하나)
2. 문제별 진단 표 (문제 / 내 상황의 증거 / 대응하는 DBMS 기능 / 우선순위)
3. 도입 로드맵 4~6단계
4. 예상되는 단점과 대비책
5. 다음에 해 볼 일 2~3가지

G1언제 쓰나

파일 시스템의 중복을 DBMS로 바꾸는 가장 작은 실험입니다. 같은 주소를 세 곳에 저장한 표와, 한 곳에만 저장하고 참조하는 표를 만들어 비교합니다.

G2실행 순서
  1. 나쁜 설계 만들기주소를 세 번 저장하는 표를 만듭니다.
  2. 값 넣고 고쳐 보기주소 하나를 바꾸고 몇 행을 고쳐야 하는지 셉니다.
  3. 좋은 설계 만들기주소를 별도 표로 빼고 참조합니다.
  4. 비교같은 변경을 다시 해 봅니다.
G3전체 코드
CREATE DATABASE IF NOT EXISTS shop
  CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
USE shop;

-- ============================================================
-- [A] 파일 시스템 방식 — 주소를 주문마다 통째로 저장한다
-- ============================================================
DROP TABLE IF EXISTS order_flat;
CREATE TABLE order_flat (
  order_id     INT PRIMARY KEY,
  customer_name VARCHAR(30),
  addr         VARCHAR(200),      -- 같은 주소가 주문 수만큼 반복된다
  product_name VARCHAR(60)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

INSERT INTO order_flat VALUES
 (1,'김철수','서울시 마포구','삼각김밥'),
 (2,'김철수','서울시 마포구','아메리카노'),   -- 중복
 (3,'김철수','서울시 마포구','커피');         -- 중복

-- 이사! 주소를 바꾸려면 관련 행을 '전부' 찾아야 한다
UPDATE order_flat SET addr = '서울시 강남구' WHERE customer_name = '김철수';
SELECT ROW_COUNT() AS 바뀐행수;      -- 3 — 하나라도 빠뜨리면 불일치

-- ============================================================
-- [B] DBMS 방식 — 주소는 한 곳, 주문은 참조만
-- ============================================================
DROP TABLE IF EXISTS orders;
DROP TABLE IF EXISTS customer;

CREATE TABLE customer (
  customer_id INT PRIMARY KEY,
  name        VARCHAR(30)  NOT NULL,
  addr        VARCHAR(200)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE orders (
  order_id    INT PRIMARY KEY,
  customer_id INT NOT NULL,
  product_name VARCHAR(60),
  CONSTRAINT fk_orders_customer
    FOREIGN KEY (customer_id) REFERENCES customer(customer_id)
    ON UPDATE CASCADE ON DELETE RESTRICT      -- 부모가 바뀌면 자식도 따라온다
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

INSERT INTO customer VALUES (1,'김철수','서울시 마포구');
INSERT INTO orders VALUES
 (1,1,'삼각김밥'), (2,1,'아메리카노'), (3,1,'커피');

-- 같은 이사! 이번에는 한 행만 고친다
UPDATE customer SET addr = '서울시 강남구' WHERE customer_id = 1;
SELECT ROW_COUNT() AS 바뀐행수;      -- 1

-- 세 주문 모두 새 주소를 본다 (값이 아니라 참조를 저장했으므로)
SELECT o.order_id, o.product_name, c.addr
FROM orders o JOIN customer c ON c.customer_id = o.customer_id;

-- 참조 무결성 확인: 없는 고객의 주문은 넣을 수 없다
INSERT INTO orders VALUES (4, 99, '없는고객주문');   -- ERROR 1452
G4라인별 해설
줄설명
order_flat파일 시스템식 설계를 그대로 옮긴 것입니다. 주소가 3행에 중복 저장됩니다.
ROW_COUNT()방금 문장이 바꾼 행 수를 돌려줍니다. 3 vs 1이라는 숫자가 이 편의 결론입니다.
FOREIGN KEY … REFERENCESorders.customer_id가 customer에 실제로 존재해야만 값을 넣을 수 있게 강제합니다.
ON UPDATE CASCADE부모 키가 바뀌면 자식도 자동으로 따라 바뀝니다. 중복을 사람이 맞추지 않아도 됩니다.
ON DELETE RESTRICT주문이 남아 있는 고객은 지울 수 없게 막습니다. 데이터가 어긋나는 것을 원천 차단합니다.
ERROR 1452참조 무결성 위반입니다. 오류가 나는 것이 정상이고, 그 오류가 데이터를 지켜 줍니다.
G5흔한 오류와 해결
오류 메시지원인해결
ERROR 1215: Cannot add foreign key constraint참조 대상 열의 타입·문자 집합이 다르거나 엔진이 InnoDB가 아님두 열의 타입과 문자 집합을 똑같이 맞추고 ENGINE=InnoDB로 만듭니다.
ERROR 1452: Cannot add or update a child row부모에 없는 값을 참조부모를 먼저 넣거나 참조 값을 고칩니다.
ERROR 3730: Cannot drop table referenced by a foreign key자식이 있는데 부모를 지움자식부터 지우거나 DROP TABLE … , …로 순서를 맞춥니다.
ERROR 1071: Specified key was too long인덱스로 잡은 문자열 열이 너무 김VARCHAR 길이를 줄이거나 접두 인덱스를 씁니다.
G6체크리스트
  • 부모 테이블을 자식보다 먼저 만들었는가
  • 참조 열의 타입이 정확히 일치하는가
  • ON DELETE·ON UPDATE 정책을 정했는가
  • 중복 저장한 표와 참조한 표의 바뀐 행 수를 실제로 비교했는가
G7미니 과제
과제order_flat에 상품 단가를 추가해 중복을 3곳으로 늘려 보세요. 그다음 정상 설계로 옮기고, "가격 인상" 한 번에 몇 행을 고쳐야 하는지 비교하면 갱신 이상이 체감됩니다.
G1언제 쓰나

같은 실험을 PostgreSQL로 합니다. PostgreSQL은 제약 조건의 이름과 동작을 명시적으로 다루는 문화가 강해, 이 편의 주제에 특히 잘 맞습니다.

G2실행 순서
  1. 스키마 지정search_path를 설정합니다.
  2. 부모 만들기customer를 만듭니다.
  3. 자식 만들기orders에 외래키와 정책을 붙입니다.
  4. 위반 실험일부러 잘못된 값을 넣어 막히는지 확인합니다.
G3전체 코드
CREATE SCHEMA IF NOT EXISTS shop;
SET search_path TO shop, public;

DROP TABLE IF EXISTS orders, customer;

CREATE TABLE customer (
  customer_id integer GENERATED ALWAYS AS IDENTITY,
  name        varchar(30) NOT NULL,
  addr        varchar(200),
  CONSTRAINT pk_customer PRIMARY KEY (customer_id)
);

CREATE TABLE orders (
  order_id     integer GENERATED ALWAYS AS IDENTITY,
  customer_id  integer NOT NULL,
  product_name varchar(60),
  CONSTRAINT pk_orders PRIMARY KEY (order_id),
  CONSTRAINT fk_orders_customer FOREIGN KEY (customer_id)
    REFERENCES customer(customer_id)
    ON UPDATE CASCADE
    ON DELETE RESTRICT
);

INSERT INTO customer (name, addr) VALUES ('김철수','서울시 마포구');
INSERT INTO orders (customer_id, product_name) VALUES
 (1,'삼각김밥'), (1,'아메리카노'), (1,'커피');

-- 이사: 부모 한 행만 고친다
UPDATE customer SET addr = '서울시 강남구' WHERE customer_id = 1;

-- [차이] MySQL의 ROW_COUNT() 대신 RETURNING으로 결과를 바로 확인한다
UPDATE customer SET addr = '서울시 서초구'
WHERE customer_id = 1
RETURNING customer_id, addr;

-- 세 주문 모두 새 주소를 본다
SELECT o.order_id, o.product_name, c.addr
FROM orders o JOIN customer c USING (customer_id);

-- 참조 무결성 실험: 없는 고객의 주문
INSERT INTO orders (customer_id, product_name) VALUES (99, '없는고객주문');
-- ERROR: insert or update on table "orders" violates foreign key constraint "fk_orders_customer"
-- DETAIL: Key (customer_id)=(99) is not present in table "customer".

-- [차이] 지연 제약 — 트랜잭션 끝에서 검사하도록 미룰 수 있다
ALTER TABLE orders
  DROP CONSTRAINT fk_orders_customer,
  ADD  CONSTRAINT fk_orders_customer FOREIGN KEY (customer_id)
       REFERENCES customer(customer_id) DEFERRABLE INITIALLY IMMEDIATE;

G1언제 쓰나

중복을 넣기 전에 찾아내고, 넣은 뒤에는 정말 중복이 없는지 확인할 때 씁니다. 마이그레이션 전 점검 스크립트로 실무에서 가장 많이 쓰입니다.

G2실행 순서
  1. 읽기평평한(중복 있는) 표를 데이터프레임으로 읽습니다.
  2. 중복 진단중복으로 낭비되는 행 수를 셉니다.
  3. 분해부모 표와 자식 표로 나눕니다.
  4. 확인분해 후에도 정보가 손실되지 않았는지 조인으로 검증합니다.
G3전체 코드
# -*- coding: utf-8 -*-
"""3주차 실습 — 중복 진단과 표 분해 (pandas)"""
import pandas as pd

# [1] 파일 시스템식으로 평평하게 저장된 표
flat = pd.DataFrame({
    "order_id":     [1, 2, 3, 4],
    "customer_name":["김철수", "김철수", "김철수", "이영희"],
    "addr":         ["서울시 마포구", "서울시 마포구", "서울시 마포구", "부산시 해운대구"],
    "product_name": ["삼각김밥", "아메리카노", "커피", "샌드위치"],
})

# [2] 중복 진단 — 같은 (이름, 주소) 조합이 몇 번 나오는가
dup = flat.groupby(["customer_name", "addr"]).size().reset_index(name="반복수")
print(dup)
print("중복으로 낭비된 행:", int((dup["반복수"] - 1).clip(lower=0).sum()))

# [3] 표 분해 — 부모(고객)와 자식(주문)으로 나눈다
customer = (flat[["customer_name", "addr"]]
            .drop_duplicates()
            .reset_index(drop=True))
customer["customer_id"] = customer.index + 1        # 대리키 부여
print(customer)

orders = flat.merge(customer, on=["customer_name", "addr"], how="left")
orders = orders[["order_id", "customer_id", "product_name"]]
print(orders)

# [4] 검증 — 조인해서 원본과 같은지 확인 (정보 손실 점검)
restored = orders.merge(customer, on="customer_id", how="left")
same = restored[["order_id", "customer_name", "addr", "product_name"]].equals(flat)
print("원본과 동일한가:", same)

# [5] 이사 시나리오 — 고칠 행 수 비교
flat_edit  = flat.copy();   flat_edit.loc[flat_edit["customer_name"] == "김철수", "addr"] = "서울시 강남구"
cust_edit  = customer.copy(); cust_edit.loc[cust_edit["customer_name"] == "김철수", "addr"] = "서울시 강남구"
print("평평한 표에서 고칠 행:", (flat["customer_name"] == "김철수").sum())
print("분해한 표에서 고칠 행:", (customer["customer_name"] == "김철수").sum())
G4라인별 해설
줄설명
groupby(...).size()SQL의 GROUP BY … COUNT(*)와 같은 계산입니다.
drop_duplicates()고객 목록을 뽑는 가장 간단한 방법입니다. 실무에서는 여기에 정규화 기준을 더합니다.
대리키 부여이름이 같은 사람이 둘이면 곤란하므로, 의미 없는 번호를 붙입니다. 6편에서 배우는 대리키입니다.
merge(..., how="left")SQL의 LEFT JOIN입니다. 자식에 부모 키를 붙이는 과정입니다.
.equals(flat)분해했다가 되돌렸을 때 정보가 손실되지 않았는지 확인합니다. 이 검증을 빼면 조용히 데이터가 사라집니다.
마지막 비교4 vs 1 — 갱신해야 하는 행 수가 이 편의 결론입니다.
G5흔한 오류와 해결
오류·증상원인해결
merge 후 행 수가 늘어남조인 키가 유일하지 않음(부모에 중복)customer에 drop_duplicates()를 했는지 확인합니다.
NaN이 생김조인 키 불일치(공백·대소문자)df[col].str.strip()으로 정규화합니다.
equals()가 False열 순서나 인덱스가 다름비교 전에 열 순서를 맞추고 reset_index(drop=True) 합니다.
SettingWithCopyWarning슬라이스에 대입.copy()를 붙입니다.
G6체크리스트
  • 중복 행 수를 숫자로 확인했는가
  • 분해 후 조인으로 원본 복원을 검증했는가
  • 대리키를 붙였는가
  • 조인 키의 공백·대소문자를 정리했는가

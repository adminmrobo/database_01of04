데이터베이스 설계 · 1주차 · 04 프로그래밍 지식이 꼭 필요할까?

코딩보다 먼저
정리하는 습관

데이터베이스를 쓰는 일에는 대부분 프로그래밍이 필요하지 않습니다. 필요한 것은 무엇을 기록할지 정하는 힘, 지키는 보안 의식, 그리고 중복을 만들지 않는 정리 의식입니다.

프로그래밍이 필요한가코딩보다 먼저보안 의식
쓰는 일 vs 만드는 일수집·분류·정리보안 다섯 원칙중복 만들지 않기
코딩보다 먼저 — 수집 · 분류 · 정리 습관
01

질문 — 반드시 프로그래밍을 배워야 할까The Question

오리엔테이션에서 가장 많이 나오는 질문입니다. 답부터 말하면 "아니다. 하지만 아무것도 안 배우면 안 된다."

1먼저 오해를 풀자

데이터베이스를 쓰는 일과 만드는 일은 다릅니다. 대부분의 직무는 쓰는 쪽입니다.

직무별로 실제로 필요한 것
하는 일실제로 필요한 능력코딩
현업 담당자필요한 값을 정확히 요청하고, 결과를 검증하기거의 없음
기획·운영무엇을 기록할지 정하고 규칙을 합의하기거의 없음
분석 담당조회(SQL)로 값을 뽑아 해석하기SQL 정도
설계 담당표를 나누고 키와 제약을 정하기SQL + 약간의 코드
개발자설계 + 프로그램과 연결하기필수
2그래도 최소한의 문법은 필요하다

SQL은 프로그래밍 언어라기보다 영어 문장에 가깝습니다. 문법이 짧고, 배우는 데 오래 걸리지 않습니다.

SELECT name, email -- 무엇을 보고 싶은가 FROM customer -- 어느 표에서 WHERE address = '부산' -- 어떤 조건일 때 ORDER BY name; -- 어떤 순서로 읽는 순서 그대로 적으면 됩니다. "고객 표에서 주소가 부산인 사람의 이름과 이메일을 이름 순서로 보여 주세요."
진짜 관문은 문법이 아닙니다 어려운 것은 무엇을 물어봐야 하는지 스스로 아는 일입니다. 그건 코딩 실력이 아니라 업무 이해와 정리 습관에서 나옵니다.
조수실습·질문

선배, 저는 코딩을 잘 못하는데 괜찮을까요?

박사설계 원리

괜찮습니다. 필요한 것은 수집·분류·정리 습관입니다. 문법은 따라옵니다.

M-RoboDB 안내

삐빅 — 단, 보안은 타협하지 마십시오. 휴먼, 개인정보는 무기입니다.

초파리 연구원코드·데이터

중복은 적게, 이름은 하나로, 빈 값의 뜻은 정해 둔다. 그게 전부다.

02

코딩보다 먼저 — 수집하고 분류하는 습관Habits Before Code

데이터베이스 설계에서 가장 오래 걸리는 작업은 코드를 쓰는 일이 아닙니다. 무엇을 담을지 정하는 일입니다.

1세 가지 습관
코딩 실력보다 먼저 자리 잡아야 하는 습관
습관하는 일이것이 없으면
수집업무에서 실제로 어떤 값이 생기는지 관찰해 모은다나중에 열을 계속 덧붙이게 된다
분류비슷한 것끼리 묶고, 무엇이 무엇에 속하는지 가른다한 표에 뒤섞여 중복이 생긴다
정리이름을 정하고, 같은 뜻은 하나로 통일한다같은 값이 여러 이름으로 흩어진다
관찰이 먼저입니다 "고객 표를 만들자"가 아니라 "현장에서 실제로 무엇을 적고 있는가"부터 봅니다. 영수증, 주문서, 메모, 엑셀 파일이 모두 재료입니다. 이 관찰을 건너뛰면 표를 세 번쯤 다시 만들게 됩니다.
2분류 연습 — 이 값은 어디에 속할까
  • 고객 이름 — 고객에 속한다 (한 사람에 하나)
  • 전화번호 — 고객에 속하지만 여러 개일 수 있다 → 따로 떼어낸다
  • 주문 날짜 — 고객이 아니라 주문에 속한다
  • 상품 가격 — 상품에 속한다
  • 주문 당시의 가격 — 상품이 아니라 주문 항목에 속한다 (나중에 가격이 바뀌어도 과거 기록은 그대로여야 하므로)

이 다섯 줄이 그대로 테이블 분할입니다. 4주차에 배울 개체·속성 찾기의 원형입니다.

3AI 시대에도 남는 능력

코드 작성은 도구가 많이 도와줍니다. 그러나 "무엇을 물어야 하는지"와 "이 결과가 맞는지"는 사람이 판단합니다.

질문을 정확히 만들 수 있는 사람이 AI도 잘 씁니다. 그 힘은 결국 정리하는 습관에서 나옵니다.

03

보안 의식 — 데이터베이스는 개인정보의 창고다Security Mindset

데이터베이스를 배우는 순간 남의 정보를 다루는 자리에 서게 됩니다. 여기서는 원칙만 잡고 갑니다.

1다섯 가지 원칙
데이터베이스를 다룰 때의 최소 보안 원칙
원칙내용흔한 실수
최소 수집목적에 필요한 값만 담는다쓰지도 않는 주민번호·생년월일을 모은다
권한 분리보는 사람·고치는 사람·관리하는 사람을 나눈다모두에게 관리자 계정을 준다
접속 정보 관리비밀번호는 코드에 적지 않는다프로그램 소스에 비밀번호를 박아 둔다
백업복구할 수 있어야 안전하다백업이 없다가 한 번에 잃는다
기록누가 언제 무엇을 했는지 남긴다문제가 생겨도 원인을 못 찾는다
절대 하지 말 것 SELECT * FROM customer WHERE name = '" + 이름 + "' 처럼 입력값을 문장에 이어 붙이지 마세요. 값은 반드시 자리표시자(?)로 넘깁니다. 이 한 줄이 SQL 인젝션을 막는 가장 확실한 방법입니다.
2권한은 이렇게 나눈다
권한 분리 예시 (개념) 역할 조회 입력 수정 삭제 구조 변경 ───────────────────────────────────────────────── 현업 담당자 ✓ ✓ ✗ ✗ ✗ 운영 담당자 ✓ ✓ ✓ ✗ ✗ 분석 담당자 ✓ ✗ ✗ ✗ ✗ 관리자(DBA) ✓ ✓ ✓ ✓ ✓ 핵심 : 필요한 만큼만 준다 (최소 권한 원칙)
3정리하면
  • 데이터는 맡은 만큼 책임이 따라옵니다
  • 편한 것과 안전한 것은 다릅니다 — 편한 설정이 사고를 만듭니다
  • 사고는 대개 실수로 납니다. 그래서 되돌릴 수 있게 준비합니다
04

정리 의식 — 중복을 만들지 않는 습관Order & Discipline

이 편의 결론입니다. 좋은 데이터베이스는 좋은 정리 습관에서 나옵니다.

1정리 의식 다섯 가지
정리 의식 — 습관과 그 결과
습관구체적으로얻는 것
한 곳에만 적는다같은 사실은 한 테이블에만 저장한다고칠 곳이 한 곳뿐이다
이름을 정한다표와 열의 이름 규칙을 처음에 정한다나중에 찾기 쉽다
같은 뜻은 하나로'고객명'과 '성명'을 섞어 쓰지 않는다합칠 때 어긋나지 않는다
빈 값의 뜻을 정한다모름 · 없음 · 미입력을 구분한다평균·집계가 틀리지 않는다
바뀐 것을 남긴다수정 이력을 기록한다나중에 이유를 되짚을 수 있다
중복을 없애면 무엇이 좋아지나 같은 값을 여러 곳에 두면 ① 저장 공간이 늘고 ② 고칠 때 빠뜨리고 ③ 어느 값이 맞는지 알 수 없게 됩니다. 이 세 문제는 뒤에서 이상현상(삽입·갱신·삭제)이라는 이름으로 다시 나옵니다.
2정리 전 · 정리 후
정리 전 — 한 표에 다 넣은 상태 주문번호 고객명 고객주소 상품명 수량 ──────────────────────────────────────────── A-001 김철수 서울 강남 콜라 2 A-001 김철수 서울 강남 과자 1 ← 고객 정보 중복 A-002 김철수 서울 강남 물 1 ← 또 중복 A-003 이영희 부산 해운대 콜라 3 김철수가 이사하면? → 3줄을 고쳐야 하고, 하나를 빠뜨리면 값이 어긋난다 정리 후 — 역할별로 나눈 상태 고객(고객번호, 이름, 주소) 주문(주문번호, 고객번호, 일시) 주문항목(주문번호, 상품번호, 수량) 상품(상품번호, 이름, 가격) 김철수가 이사하면? → 고객 표의 1줄만 고치면 끝난다
